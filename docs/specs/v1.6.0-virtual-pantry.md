# v1.6.0 — Virtual Pantry

Status: Approved October 29, 2026. This document specifies future work; it does not mark the release shipped or change the package version.

## Product intent

Virtual Pantry answers **“Do I have this?”** A user records which ingredients they have in their pantry, fridge, or freezer, maintains that list themselves, and receives recipe suggestions informed by those answers. Signed-in inventory persists across sessions and devices.

Availability is a boolean chosen by the user. Quantity is optional context, never a prerequisite for entry or the source of availability. Selecting, planning, saving, or cooking a recipe does not change inventory.

## Release scope

- Rename the user-facing Virtual Freezer feature to **Virtual Pantry** throughout navigation, inventory, recipe badges, account flows, help, and current API documentation.
- Provide ingredient search, optional quick-add suggestions, and custom ingredient entry.
- Support explicit Yes/No availability and optional storage location, quantity, unit, and use-by date.
- Preserve private guest use, account persistence, offline edits, and explicit guest-to-account import.
- Use available ingredients in recipe selection, ingredient labels, shopping lists, and estimated additional grocery costs.
- Migrate existing freezer inventory and manual on-hand selections without losing user data.

Out of scope: automatic consumption or deductions, quantity sufficiency checks, recipe-based reservations, shared household inventory, expiry notifications, automated substitutions, and new inventory-driven AI calls. Existing account and privacy controls continue to apply. Purchase suggestions (including “Buy 2: Prep 1, Freeze 1”) and cooking actions are decoupled from inventory; only explicit pantry management changes availability or optional inventory details.

Follow-up releases:

| Release | Planned extension |
| --- | --- |
| v1.6.1 | Speech-to-inventory: dictate items, review/correct recognized ingredients, and confirm additions. Unmentioned items remain unchanged. |
| v1.6.2 | Barcode scanning: resolve scanned products to generic ingredients, with confirmation or correction where needed. Add dynamic pricing for pantry staples. |

These follow-ups use the same inventory model; v1.6.0 includes no microphone, camera, transcription, or barcode-service integration.

## Entry and inventory experience

Virtual Pantry is accessible from the dashboard on mobile and desktop. Its primary list shows items marked Yes, with search and a way to view items marked No. Each row exposes the ingredient name, a clearly labeled Yes/No control, optional location, and an edit action. Users can delete an entry separately from marking it No.

An empty pantry offers search/add and optional quick-add suggestions. Suggestions are shortcuts, never preselected inventory, required staples, or an assertion about what a household ought to own. Users can complete setup without using them.

Search covers the generic ingredient catalog and the user's custom entries, independent of current deals, stores, or priced commodities. Adding a search result marks it Yes. Adding an existing ingredient reuses its entry and sets it to Yes without creating a duplicate or clearing optional details. A user can instead explicitly create or retain a No entry.

If search has no suitable result, **Add custom ingredient** accepts a user-provided name. Custom items have the same availability and editing controls as catalog items. They remain usable without external services or API keys.

Optional fields are collapsed or secondary to the availability control:

| Field | Behavior |
| --- | --- |
| Storage location | Pantry, Fridge, Freezer, or unspecified. One optional location per entry for this release. |
| Quantity | Optional finite, nonnegative number. No automatic arithmetic or recipe deductions. |
| Unit | Optional text, allowing natural labels such as cans, bags, g, or lb. No conversion required. |
| Use-by date | Optional valid calendar date, without timezone shifting. Display as user-entered context. |

Neither zero quantity nor a past use-by date silently changes Yes to No. Availability remains explicit; dates do not certify food safety. Marking an entry No preserves its optional details until edited or deleted.

Proposed initial validation limits: ingredient names 1–120 trimmed characters and units up to 40 characters; reject blank names and invalid numeric/date values with inline errors. These are implementation defaults, not restrictions on cuisines or ingredient families.

## Ingredient identity and inclusive catalog

Use generic food identities rather than brands or packaged-product SKUs. Support ingredients across food traditions without treating one household pattern as the default. Exact catalog seed coverage should be reviewed during implementation and must not block custom entry.

Normalize case and whitespace for duplicate checks and support reviewed alternate names. Preserve distinctions relevant to cooking: rice varieties, flour types, and different bean preparations must not be silently collapsed into one interchangeable ingredient. A broad match such as “rice” must not automatically claim the user has every rice variety.

Catalog ingredients have stable IDs independent of display names and market pricing records. Link to existing canonical recipe/commodity identities where the meaning matches. Custom names remain private to their owner and do not automatically become shared catalog entries.

For v1.6.0, recipe matching uses verified identity mappings. Do not use fuzzy name similarity or AI to silently turn a custom item into another ingredient. Unmapped custom entries remain visible and manageable; explain that they do not yet affect recipe matching. Allow users to choose a catalog match explicitly when editing, with duplicate handling.

## Availability and recipe behavior

An entry marked Yes is available. No entries and ingredients without an entry are not counted as available. Internally preserve the distinction between an explicit No and an unrecorded ingredient; UI wording for the latter should be “Not marked available” rather than a claim about the user's kitchen.

- Reuse existing recommendation behavior that favors on-hand ingredient matches, while preserving dietary restrictions, serving preferences, and explicit user selections.
- Label matched ingredients **Already have** and other required ingredients **Need to buy** or **Not marked available**, as appropriate to context.
- A recipe can show “You have 4 of 7 ingredients,” counting distinct required ingredient identities consistently. Count optional ingredients separately; unmapped ingredients cannot count as available.
- Omit ingredients marked Yes from generated shopping needs. Availability is an assumption of coverage, even when an optional quantity is small or absent. Do not calculate partial shortfalls.
- Label the resulting estimate **Estimated additional grocery cost** and explain that it assumes marked ingredients are on hand. Avoid presenting stocked ingredients as free food or claiming measured savings from their presence.
- Preserve cost-estimate uncertainty for missing prices. Custom entries do not acquire fabricated offers or prices.
- Include pantry staples (such as oils, spices, and broth) in ingredient coverage and shopping needs using explicit ingredient identities. For v1.6.0, assign reasonable fixed USD estimates per recipe-use unit; label them as static estimates, not observed store prices. Marked-available staples are omitted from additional grocery costs. Dynamic staple pricing is deferred to v1.6.2.
- Refresh recipe and shopping-list results after an availability change. Existing saved recipes remain intact; their current availability display is derived from current inventory.
- Keep a deterministic recipe path without AI keys. Any existing AI suggestion path must receive the same availability interpretation without bypassing authentication requirements.

The pantry becomes the single source of truth for availability. Existing dashboard on-hand toggles must update the corresponding pantry entry rather than maintain a conflicting parallel list.

## Persistence, privacy, and sync

The app already contains account-linked freezer storage and sync. Extend that foundation and verify the full user-visible behavior rather than treating persistence as a newly invented subsystem.

- Signed-in reads and writes derive ownership from the authenticated session. Reject caller-supplied identity as authentication and enforce account isolation at every storage boundary.
- Reloading, closing/reopening the browser, signing out/in, and signing in on another device restore the account's inventory after a successful save.
- Guest mode remains functional without an account or API keys, with local persistence scoped to the private guest context. Explain that cross-device recovery requires sign-in.
- Offer an explicit guest import after sign-in. Do not silently upload guest entries or attach them to whichever account signs in next. For duplicate identities, preserve the account entry and its details; preview/report duplicates so the user can edit them afterward. Repeating an import must not duplicate items.
- Show **Saved**, **Pending sync**, or **Couldn’t sync — Retry** as appropriate. Never acknowledge a failed write as saved. Preserve pending edits across offline periods and reloads.
- Bind cached data and queued mutations to their originating account. Signing out or switching accounts must not display, merge, or replay another account's data.
- Retry mutations idempotently. Use per-entry revisions to detect concurrent edits: a stale write must not silently overwrite a newer remote edit or resurrect a deleted entry. Retain the pending change and ask the user to choose the current remote value or their edit before retrying against the latest revision.
- Include pantry entries in account export and deletion. Personal inventory must never appear in public market-data views, shared caches, or logs intended for public data.

## Logical data model and migration

Each entry has a stable entry ID, owner scope, optional catalog ingredient ID, display name, boolean availability, optional location/quantity/unit/use-by date, and server-managed revision/update metadata. Custom entries do not require a catalog ID. Enforce one entry per catalog identity within an owner; use normalized names to prevent duplicate custom entries within that owner. Different owners may use the same names independently.

Optional metadata never controls availability. Avoid retaining a required pounds/dozens quantity, price, store, or savings field in the new inventory contract. Preserve legacy purchase/arbitrage metadata separately where existing features still need it.

Migration requirements:

1. Convert existing positive-quantity freezer records to Yes entries with location Freezer; preserve their quantities and units as optional metadata. Convert retained zero-quantity records to No.
2. Convert existing manual on-hand selections to Yes entries with unspecified location. Merge overlaps with migrated freezer records, retaining freezer location and details. Any positive legacy source makes the merged entry Yes.
3. Preserve legacy details when multiple records map to one ingredient; do not blindly sum incompatible units or discard original purchase records.
4. Apply migration to both account data and eligible guest caches within their original ownership scope. Make it repeatable and safe after interruption, with stable identity mapping and no duplicate imports.
5. Avoid data loss during rollout or interaction with older clients. Define and test compatibility for legacy freezer APIs, sync payloads, and cache keys before enabling the new UI. Old quantity-based writes must not silently erase new pantry availability or metadata; reject unsupported writes explicitly if safe translation is impossible.

Implementation should choose the schema and endpoint migration in a technical plan. The public product name need not force an immediate destructive rename of every historical table or identifier. Update current OpenAPI contracts and generated copies together; keep historical release notes historically accurate.

## Acceptance criteria

1. A guest and a signed-in user can each add a catalog ingredient using only its name; it appears as Yes without quantity, price, or location.
2. Optional quick-add suggestions and search coexist. No starter ingredient is automatically marked Yes. A custom ingredient outside the catalog can be added and retained.
3. Yes/No changes, edits, and deletion persist across reloads. Account data also survives a fresh authenticated session and loads on a second device.
4. Setting quantity to zero, leaving it blank, or entering a past date does not change explicit availability. Invalid values produce recoverable errors.
5. Re-adding an ingredient does not duplicate it. Marking No preserves details; marking Yes restores its use in recipe matching.
6. Recipe coverage, shopping needs, and additional-cost estimates follow boolean presence, regardless of optional quantities. Dietary restrictions remain enforced. Unmapped custom entries do not falsely count as matches.
7. Viewing, saving, planning, or cooking recipes never deducts or changes inventory.
8. Offline edits survive reload and retry without duplication. Failed saves remain pending; stale concurrent changes require resolution without silent loss or resurrection.
9. Account A's data and pending edits cannot be read or written as account B. Guest import requires an explicit action and handles duplicates predictably.
10. Existing freezer and manual on-hand data migrate once, retain ownership and useful metadata, and do not reappear as duplicates after subsequent logins.
11. Inventory controls work with keyboard and screen readers, have explicit accessible availability labels, and remain usable on narrow mobile screens. Loading, empty, search-no-results, and save-error states provide clear next actions.
12. Account export/deletion and documented APIs cover the new model. Keyless local operation and deterministic recipe suggestions still work.

## Implementation slices and verification

Suggested order: inventory contract and migration; persistence/sync and account boundaries; catalog/custom search and management UI; recipe/shopping integration; naming/docs and end-to-end verification. The spec does not authorize shipping incomplete migrations or broadening scope into speech or scanning.

Use focused unit tests for boolean matching, identity/deduplication, validation, and migration. Add integration coverage for account isolation, guest import, retry durability, concurrent edits/deletes, export/deletion, and legacy compatibility. Exercise the complete add → save → reload → recipe/shopping flow in smoke coverage, including a quantity-free entry and keyless guest use.

Before implementation PRs merge, run the repository's required typecheck, lint, unit tests, smoke tests, and build, plus regression tests for the production release. Verify real account persistence across sessions/devices in staging and complete the required CI, preview, and Claude review gates. Release documentation and the version bump belong to the release workflow, not this specification.

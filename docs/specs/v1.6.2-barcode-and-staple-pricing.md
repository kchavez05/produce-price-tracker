# v1.6.2 — Barcode Pantry Entry & Staple Pricing

Status: Approved by the maintainer in chat, November 8, 2026. Provider selection, launch coverage and technical contracts remain open implementation gates under section 9. Approval establishes the product contract; it does not mark implementation or release complete.

## 1. Product intent and baseline

Let a user scan or type a packaged food's barcode, review its proposed generic pantry identity, and explicitly confirm an addition. Improve recipe staple estimates with qualifying observed prices where evidence supports the calculation.

Build on the released v1.6.1 catalog of 222 identities and the existing [Virtual Pantry contract](v1.6.0-virtual-pantry.md), [ingestion standards](usda-catalog-ingestion.md#10-brandedapi-boundaries-for-v162), and [review guide](../code-review.md). Product discovery, generic identity, ownership, recipe compatibility and price evidence are separate facts.

The current implementation uses fixed recipe-use estimates in `src/lib/pantry/requirements.ts` and `src/lib/pantry/recipe.ts`, with staple requirements in `src/data/recipe-staples.ts`. The pricing work must update recipe totals, detail rows, saved-recipe reevaluation and shopping needs consistently rather than replacing only a display label.

## 2. Scope

| Included | Boundary |
| --- | --- |
| Camera capture and manual barcode entry | Web/PWA experience; no native application migration |
| Packaged-product lookup and proposed generic matches | Reuse accepted pantry identities; no automatic generic-catalog expansion |
| Review, correction and explicit confirmation | Reuse existing Yes/No, duplicate, conflict and sync behavior |
| Dynamic staple recipe-use estimates | Only reviewed ingredient/source/unit combinations with qualifying evidence |
| Clearly labeled static estimates and unpriced states | Basic pantry use and deterministic recipes require no account, camera or provider key |

Speech entry, AI access/funding redesign, billing, shelf-tag OCR, receipt parsing, in-aisle competitor-price comparison, nationwide collection, recurring ingestion, nutrition imports, dietary certification, automatic substitutions, inventory deductions and unrelated UI refinements are outside this release. Any additional catalog identity or conversion requires a separate reviewed decision.

## 3. Barcode entry flow

1. The pantry offers **Scan barcode** and **Enter barcode** alongside ingredient search and custom entry. Camera access is requested only after the user chooses scanning.
2. Capture or enter a code, validate it, and show a lookup state. Manual entry remains available when camera access is denied, unavailable or unsupported. Ingredient search/custom entry remains available when lookup cannot run.
3. Show the resolved product's name, brand, package information, source and applicable market when supplied. Distinguish missing metadata from known facts. Present a proposed generic ingredient separately; do not disguise the branded name as a catalog identity.
4. Let the user accept a candidate, search for another catalog identity, or create a private custom ingredient. Ambiguous matches require a choice; no candidate is silently confirmed. Explain that unmapped custom entries do not establish recipe coverage.
5. **Confirm addition** explicitly saves the chosen identity as Yes through the existing pantry mutation path. Quantity, unit, location and date remain optional. Cancellation changes no inventory.
6. Show the normal saved/pending/error state and refresh recipe coverage and shopping needs after confirmation. Allow another scan through a deliberate action.

Capture pauses after a valid decode so repeated frames cannot generate additions or repeated requests. Changing the code, leaving the flow, changing account or cancelling invalidates pending results; a late response must not replace the current review or write inventory. Stop camera tracks when capture closes, the component unmounts or the page is hidden; resumption must be deliberate.

An existing Yes entry is reused without clearing optional details. An existing No entry must be visibly identified as No during review, and only explicit confirmation changes it to Yes. Repeated confirmation/retry cannot duplicate entries; stale concurrent changes follow the existing revision-conflict flow. A product's package size is lookup context, not an automatic inventory quantity or increment.

Keyboard input, readable inline errors, focus management, accessible status messages and a narrow-screen review flow are required. Camera use is never the sole way to complete entry.

## 4. Product identity and mapping

Barcodes are strings throughout capture, requests, storage and fixtures. Preserve the original value and leading zeros. The technical plan must define supported symbologies, length/check-digit validation, accepted human formatting, and any verified equivalence between representations. Do not cast to a number, apply blanket padding, or interpret arbitrary scanned text as a URL to fetch. Variable-weight, store-internal, unsupported and invalid codes receive an explicit unsupported/invalid result and manual fallback; price-encoded barcode parsing is outside the initial scope.

Maintain a product record independently of pantry entries. Its logical fields include source record ID/version, original barcode and validated lookup representation, product/brand labels, package amount/unit if known, market/country, source publication/update dates when available, retrieval time, and source attribution. Retrieval time is not proof of product currency. Retain provenance and superseded versions under the provider's permitted retention terms.

A mapping candidate identifies an accepted generic ingredient, the source product revision, relevant food/form evidence, mapping rule/version and ambiguity. Automated suggestions use reviewed deterministic rules; there is no AI mapping dependency. User correction applies to that user's confirmed entry and must not automatically publish a shared mapping rule. Persisting reusable personal mapping preferences is deferred unless separately specified with ownership/export/deletion behavior.

Require evidence for cooking distinctions such as dry/canned, whole/ground, raw/cooked, dairy moisture/flavor and mixed products. Brand names, broad categories, keyword overlap or a product's ingredient list do not establish equivalent generic identities. A sauce containing garlic does not mark garlic available; a blend does not establish its components. User choice cannot create new shared recipe-compatibility edges or override reviewed recipe exclusions.

For multiple source records, document applicable market, revision selection and tie handling. Missing products, contradictory records and unresolved ties lead to correction/custom entry rather than an arbitrary match. Lookups and source refreshes never mutate inventory.

## 5. Lookup service, privacy and offline behavior

The maintainer confirmed the downloaded USDA branded snapshot as the initial product-discovery source on November 9, 2026. Coverage, indexing, revision handling and operations still require the feasibility gate in section 9. Do not assume a new credential, license, paid service or production quota is already available.

- Keep provider credentials and provider calls server-side. Bound input sizes, timeouts, retries, response parsing and cache growth. Honor provider throttling with bounded backoff and expose retryable failures. Final abuse controls and cache policy must be documented before enabling a public lookup endpoint.
- Return distinct recoverable outcomes for invalid/unsupported code, not found, ambiguous product/mapping, offline, missing service configuration, throttling and upstream failure. A failure must not be cached as a confirmed missing product indefinitely.
- Camera decoding is local; do not upload or retain frames. Shared caches may contain permitted public product records, never account inventory, private custom names or personal scan histories. Avoid recording raw user scan activity in analytics/logs; operational diagnostics must be minimized and redacted.
- Manual pantry search/custom entry and previously saved inventory remain usable with no keys and no network. An uncached barcode cannot promise a product result offline. Where a permitted product record is cached, disclose its age and allow review/correction; never present it as a fresh lookup.
- Cancelling or losing a product lookup does not create a pantry mutation. A confirmed addition uses the existing durable owner-bound queue and survives offline/reload without duplicate replay.
- Guest import stays explicit. Account switches discard the previous owner's unsaved review and cannot replay that owner's pending additions. Any new owner-specific stored metadata must be covered by export and deletion.

## 6. Dynamic staple pricing contract

### Eligible evidence

Only a reviewed observed retail offer applicable to the requested market and selected store context may supply an observed staple estimate. It must identify the food/form, currency, actual package price and compatible net quantity, source, store/location, observation date, validity/freshness and purchase conditions. Resolve source revisions without counting them as additional independent observations.

A barcode/product record alone supplies no current price. FDC identity/nutrition references, national benchmarks, group history, scraped labels without usable terms, and estimated regular prices cannot become a current local quote. A pantry match does not certify that a price offer qualifies for that same identity. Preserve v1.6.1 exact-offer rules independently.

Exclude offers whose required membership, coupon or multi-buy conditions are unsupported by the current pricing context; do not advertise their conditional unit price as generally available. Document a deterministic selection/tie rule among eligible selected-store offers. Selection must not change the pinned recipe identity, reviewed alternative or dietary behavior simply to find a cheaper food.

### Recipe-use calculation

For an eligible quote:

`recipe-use estimate = package price × required amount / compatible package amount`

The numerator and denominator must describe the same food and measurement basis. Define exact mass-to-mass and volume-to-volume conversions explicitly; distinguish fluid ounces from mass ounces. Mass/volume density conversions, drained yields, concentration/dilution, bone/skin losses and each-to-weight conversions are disallowed unless supported by a separately reviewed food-specific rule. Preserve current unpriced behavior when no safe conversion exists.

Reject invalid, nonfinite, negative, zero-denominator or overflowing values. Zero-price observations need explicit source evidence; absence never becomes zero. Use a consistent money precision/rounding policy, defined in the technical plan, across detail rows and totals. Calculate with retained precision and round at documented display/aggregation boundaries.

These are allocated recipe-use costs, not a promise that a user can purchase part of a package. Show the package price/size separately when offering a shopping link. Full-package checkout totals and quantity sufficiency remain outside scope. Merely having less optional pantry quantity than a recipe requires does not create a shortfall.

### Fallback and presentation

Apply this order independently for each missing required staple:

1. Current qualifying observed offer with a supported conversion: observed recipe-use estimate.
2. No qualifying observed calculation: existing reviewed static recipe-use estimate, if supported for the requirement's unit, explicitly labeled **Static estimate**.
3. Neither: **Price unavailable**, with the ingredient included in the incomplete-estimate indicator.

Do not introduce new static values or silently extend an estimate to a different identity/unit. An expired or out-of-scope quote cannot remain labeled current; reevaluate fallback when date, market, selected stores, offer data or serving count changes. An offline last-seen quote may remain inspectable with its dates but cannot bypass freshness/validity checks.

Available ingredients are omitted from additional grocery costs under the existing boolean model. No acquisition cost or measured savings is inferred from ownership. Required uncovered ingredients retain shopping needs even when unpriced; optional ingredients remain outside required totals unless the existing recipe contract selects them as required.

Recipe details expose basis per ingredient, source/store and dates for observations, package evidence and conversion. Mixed totals disclose **Includes static estimates**; unknown prices disclose **Incomplete estimate**. Having a static estimate for every missing ingredient means the estimate is complete, not that every price is observed. Avoid assigning a single observed label to a mixed total.

Current recipe totals, shopping details and saved-recipe reevaluation must use the same price context. Saved recipes retain stable requirements and provenance where needed for explanation; current prices are derived without overwriting the saved recipe or the user's inventory. Observed staple costs must not fabricate a regular-price comparison, discount percentage or stock-up signal.

## 7. Persistence and rollout compatibility

Prefer the existing confirmed pantry-entry contract without product fields. Product metadata is not required for availability, account save or offline recovery. The technical plan must justify any new private metadata and define its old-client preservation, export/deletion and migration behavior before introducing it.

Do not rename or delete accepted catalog IDs. New shared product/cache storage is separate from owner inventory. Any necessary database migration is additive and tested against an isolated staging database before hosted application; shared Preview/Production storage cannot substitute for destructive migration testing.

Document independent rollout/disable controls for lookup/camera and dynamic pricing. Disabling lookup preserves confirmed entries and manual entry. Disabling observed pricing restores the prior static/unpriced behavior without rewriting inventory, saved recipes, source evidence or historical prices. Verify compatibility with older clients and generated OpenAPI copies for any API changes.

## 8. Acceptance matrix

| Area | Required evidence |
| --- | --- |
| Entry | Camera and typed code reach the same review flow; leading zeros survive; denial/unsupported device and invalid/unsupported codes recover through manual entry |
| Lookup | Found, missing, conflicting revisions, wrong market, ambiguous match, stale cache, offline, throttled and service-error cases produce distinct usable outcomes |
| Mapping | Review preserves cooking forms and mixed-product boundaries; correction/custom entry works; component ingredients never become owned automatically |
| Confirmation | Cancel/late response changes nothing; existing No requires explicit Yes confirmation; duplicate frames, double-clicks and retries do not duplicate entries or erase details |
| Ownership | Guest isolation, explicit guest import, two-account separation, account switches, failed saves, reload/retry, stale revisions and tombstones retain existing behavior |
| Prices | Compatible mass/volume examples pass; fluid/mass ambiguity, unknown package amounts, invalid denominators, unsupported yields and wrong food/store/market/conditions reject observation use |
| Freshness | Expired, stale, revised and unavailable offers follow the documented selection/fallback policy; filtering stores and changing market removes inapplicable quotes |
| Presentation | Observed/static/unpriced/mixed totals agree across recipes and shopping; source dates and package cost remain distinct from allocated recipe-use estimates |
| Pantry semantics | Yes suppresses additional need regardless of optional quantity/date; explicit No precedence, recipe exclusions, pinned choices and dietary restrictions remain intact |
| Compatibility | Saved-recipe reevaluation, owner exports/deletion and older-client behavior pass; disabling each feature preserves data and restores the supported fallback |
| Devices | Keyboard/screen-reader flow and narrow mobile layout pass; real mobile camera permission, capture, close/resume and typed fallback are verified on the documented launch device/browser matrix |

Use meaningful unit fixtures for code validation/mapping, price qualification/conversion/fallback and deterministic selection. Smoke tests cover lookup → correction → confirmation → save/reload → recipe/shopping updates. Regression coverage includes mixed-food admission, ownership/retry boundaries, saved recipes and stale prices. Separate provider contract fixtures from live checks so CI and keyless operation do not depend on upstream availability. Record real-device and authenticated second-client results separately from mocked tests, including verification limits and cleanup.

## 9. Decisions required before implementation

### November 9 decisions and coverage checkpoint

The maintainer confirmed USDA snapshot-first product discovery, King Soopers as the first observed-price source in the existing Mead/Firestone/Longmont market (subject to access and coverage verification), and iPhone Safari plus Android Chrome as camera launch targets. Initial qualifying prices are unconditional shelf prices observed on the same America/Denver calendar day at the selected location; exclude membership, digital-coupon and multi-buy prices. Earlier expiry or another failed qualification still disqualifies an offer. Retain static/unpriced fallback.

The [staple coverage audit](../research/v1.6.2-staple-coverage-audit.md) enumerates all 43 current staple identities across 12 recipes, conversion barriers, USDA discovery examples and remaining live-feed verification. It verifies no live prices and approves no mapping or conversion. Decoder choice, barcode support, exact launch mappings, quote contracts, calculation conventions, operations and rollout controls remain open; earlier chat recommendations are proposals unless explicitly accepted.

The subsequent [Production coverage checkpoint](../research/v1.6.2-live-staple-coverage.md) resolves Kroger access and records a bounded 17-identity/four-location sample, including corrected location IDs. It distinguishes source regular-price/package evidence from approved unconditional quote admission; those price semantics, exact forms and conversion decisions still require review before implementation.

The [pricing qualification packet](../research/v1.6.2-pricing-qualification-packet.md) proposes eight review decisions, 13 initial ingredient identities, 50 synthetic expected vectors, and conditional per-recipe reach. It remains unapproved and inactive. Provider currency/conditions, use-case and retention permissions are external gates; approving or merging the packet cannot establish those facts or permissions.

| Decision | Required deliverable |
| --- | --- |
| Product provider and lawful usage | Validate the selected USDA snapshot with measured target-market/product coverage, attribution/license terms, caching/retention rights, index/storage design and outage behavior; document any proposed supplemental source separately |
| Barcode support and decoding | Specify supported code formats, validation/equivalence rules, camera decoder strategy, launch browsers/devices, dependency/bundle impact and manual fallback |
| Initial mapping coverage | Versioned representative product fixtures and exact reviewed generic mapping rules, including ambiguous/mixed/unsupported examples; no silent expansion of the 222-identity catalog |
| Initial staple pricing coverage | Exact ingredient IDs, source/store/market coverage, permitted units/conversions, validity/freshness thresholds, source conditions, selection/tie rules and explicit unpriced/static gaps |
| Lookup access and operations | Guest/account policy, request limits, bounded caching/retries, secret configuration, attribution, permitted retention and diagnostic policy |
| Technical integration | Request/response contracts, price-basis types, shared recipe/shopping evaluator, precision policy, cache invalidation, storage needs, rollout controls and rollback procedure |

These are implementation gates, not claims that a provider or price feed is ready. Proposed default: allow bounded non-AI lookup for guests and accounts, with equal manual fallbacks; confirm provider economics and abuse controls before activation. No app-funded AI endpoint is added by this spec.

Both barcode entry and meaningful dynamic staple coverage remain release requirements. If feasibility cannot establish either, bring an explicit scope revision to the maintainer rather than declaring success with only fallback behavior. Launch coverage must be reviewed against representative target products and affected recipes; do not pick an arbitrary count and imply universal coverage. Set the release date after this checkpoint.

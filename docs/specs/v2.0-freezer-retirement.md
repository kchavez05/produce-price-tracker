# v2.0 Prerequisite: Legacy Virtual Freezer Retirement — Draft Plan

Status: **Draft — planning only; not approved.** Prerequisite for [M3 dashboard decomposition](./v2.0-m3-dashboard-decomposition.md) (decisions 4 and 14, owner, 2026-11-12). Tracked in [#700](https://github.com/kchavez05/produce-price-tracker/issues/700), related to the v2.0.0 release parent [#682](https://github.com/kchavez05/produce-price-tracker/issues/682). Builds on the shipped Virtual Pantry design ([v1.6.0 specification](./v1.6.0-virtual-pantry.md)).

## 1. Purpose and Scope

Make the pantry-enabled path the only path: turn Virtual Pantry on in Production, then remove the legacy Virtual Freezer code, API and storage in stages, without losing anyone's data or breaking sync, ownership or zero-key behavior. This is a behavior, data and public-API change, which is why it ships separately from M3 and is not behavior-preserving.

In scope: Production activation of `PANTRYBOT_PANTRY_ENABLED`; the fate of existing Freezer lots; removing the flag-off dashboard paths, `/api/freezer`, Freezer fields in sync, AI-plan and digest inputs, and the local fallback tables; the OpenAPI, terms and documentation updates; the test changes.

Out of scope: redesigning Pantry (M4), the barcode and camera flags (independent), changing the pantry data model or migration RPC semantics, and the bring-your-own-key AI input (v1.7).

## 2. Baseline (develop at `6b5e124`, surveyed 2026-11-12)

- **Flag state.** `PANTRYBOT_PANTRY_ENABLED=true` is set only for Preview (`develop`); Production runs with it off. `docs/usda-catalog-integration.md` says to keep it false on hosted environments until migrations are verified, and the v1.6.0 release notes say to enable it only after migrations and database checks succeed.
- **Shared database.** The Supabase project is the single environment for Preview and Production. `list_migrations` (read-only, 2026-11-12) shows all 17 repo migrations applied, including `virtual_pantry_persistence` and every pantry catalog migration, under different version stamps than the repo filenames (for example `20261030204602` against `20261029171953`). Their content should be confirmed identical before activation. **Not known:** row counts (users, Freezer rows, users already migrated); a production read query was blocked in this session, so section 8 gives an owner-run aggregate query.
- **How migration works today.** It is lazy and client-driven. When a signed-in user opens Pantry with the flag on, `usePantry` reads the pantry RPC; if no migration marker exists it prepares entries from the legacy lots and manual on-hand IDs (`migrateLegacyPantry`) and posts them with the exact legacy source for the server to compare (`legacy_changed` aborts a stale snapshot). The server stores the original source, unchanged, in `user_pantry_migrations`. Guests migrate their device cache. Users who never return while the flag is on stay unmigrated, with their lots intact in `user_freezer_items`. Pending older offline edits must sync first or the migration stops with a retry message.
- **Fence.** After a user is migrated, a database trigger (`pantry_fence_freezer`, `pantry_fence_preferences`) rejects writes to `user_freezer_items` and to on-hand preferences with `pantry_upgrade_required`, so older clients cannot overwrite pantry state. **Consequence:** turning the flag back off after migrations is not a safe rollback (legacy writes are rejected for migrated users). Rollback is forward-fix only.
- **The migration RPC reads the legacy table** (`user_freezer_items`) to build and compare the source, so the table cannot be dropped until every user is migrated or the RPC changes.
- **Where Freezer lives.** About 400 mentions across 30 files. Largest: `MealPrepDashboard.tsx` (148), `src/lib/openapi/spec.ts` (50, four `/api/freezer` operations), `src/lib/supabase/session.ts` (34), `src/app/api/freezer/route.ts`, `src/lib/db/sqlite.ts` (27; tables `freezer_inventory` and `user_freezer_items`), `useUserSync` (18), `meal-prep-matcher` (15), `AccountModal` (11), `src/lib/sync/queue.ts` (10), `src/lib/pantry/legacy-queue.ts` and `migration.ts` (the bridge, to keep), `ai-meal-plan` and `dashboard` routes (already pass an empty Freezer when the flag is on), `terms/page.tsx`, rate-limit key `api-freezer-write`, 43 documentation mentions.
- **Client storage.** `localStorage` keys `pantrybot_virtual_freezer_v12`, `pantrybot_virtual_freezer_v14:<id>` and `mead_on_hand_ids_v04` hold legacy state; the guest and queue readers (`parseGuestFreezer`, `legacyQueueNeedsUpgrade`) are the migration bridge.
- **Account data rights.** Export includes `virtualFreezerInventory` and the legacy archive when present; delete cascades from the parent user row. Both must keep covering legacy data until it is gone.
- **Tests that touch Freezer:** about 130 mentions across 20 files, notably `tests/regression/backend/freezer-lifecycle.test.ts`, `tests/regression/frontend/dashboard-sync.test.ts` (which uses a freezer fixture for sync coverage), `tests/unit/frontend/sync-queue.test.ts`, `tests/unit/backend/pantry-foundation.test.ts`, `account-sync-gdpr`, `session-isolation` and `security-boundaries`.
- **Not Freezer storage (keep):** the `freezerFriendly` recipe attribute, the "Buy 2: Prep 1, Freeze 1" deal prompt (in pantry mode it is already a purchase suggestion that tells the user to update the pantry explicitly), and the pantry location value `FREEZER`.

## 3. Approach: Four Stages

1. **Stage 0, readiness.** Owner-run aggregate checks on Production, migration content comparison, backup, and a Preview soak with a signed-in migrated account. No code.
2. **Stage 1, activate.** Set `PANTRYBOT_PANTRY_ENABLED=true` in Production and redeploy once v1.6.2 is released and Stage 0 is clean (before v1.7). No code removal. Migration then proceeds lazily per user. Soak for at least one release cycle while monitoring migration errors and the unmigrated-user count.
3. **Stage 2, remove legacy surfaces (code).** Delete the flag-off paths and the Freezer API, UI, sync fields and inputs, in separately reviewed PRs (section 7). Keep the migration bridge, the legacy tables and the export of legacy data. Deprecate the public API as in decision 5.
4. **Stage 3, drop legacy storage (later, separate).** After a retention window and a report showing no unmigrated users with data, remove the bridge, the fence triggers, the table and the SQLite fallback tables in their own migration PR. Not part of v2.0.

## 4. Behavior That Must Not Change

- Guest data stays private to its device and account; a cloud error never acknowledges a pending change; queued changes stay bound to the account that created them; stale clients get an explicit error and keep their queued data instead of being acknowledged and dropped.
- Zero-key behavior: the app works with no Supabase and no API keys; guest Pantry works from the device cache (verify the keyless guest path in the pre-activation tests).
- Migration never discards original lots (the archive keeps the exact legacy source).
- Account export and delete keep covering all legacy data until it is gone.
- Pricing and score math are unchanged; "already have" ingredients still cost $0 marginal in plans.

## 5. Product Consequences to Accept

- **Banked-savings tracking goes away.** The Freezer records quantity, cost basis and estimated savings per lot; Pantry is a yes/no list with no costs. The dashboard's Freezer summary (items, weight, cost basis, estimated savings) and the "From Virtual Freezer" banked-value copy in meal plans disappear. The data is preserved in the archive and in exports but not shown.
- **Quantities become availability.** Existing lots migrate as available entries; a lot's quantity does not carry over as an amount (the post-MVP "pantry amounts" idea in the flows document would revisit this).
- **Older clients and offline queues** must upgrade; the fence already enforces that for migrated users.

## 6. Risks

- **Unmigrated users.** Users who never open Pantry after activation keep lots only in the legacy table. Mitigation: do not delete storage until the unmigrated report is clean or the owner accepts the loss; Stage 3 is separate.
- **Rollback.** Flag-off after migration is unsafe (section 2). Mitigation: Preview soak, backup, forward-fix only, and the flag as a kill switch only during the Stage 1 soak before any user migrates; it is deleted with the Stage 2 code (decision 7).
- **Migration failures at scale.** Interrupted migrations, pending older offline queues, catalog match failures (`needsCatalogMatch`). Mitigation: existing resumable design; monitor the error rate during the soak.
- **Public API break.** `/api/freezer` is documented in the OpenAPI spec and the API console. Mitigation: decision 5.
- **Shared database.** No isolated environment exists; migration tests on Production-adjacent data are risky. Mitigation: aggregate checks only, a dedicated test account, and no bulk scripts without the owner's go-ahead.
- **Lost test coverage.** Removing Freezer tests could drop sync and ownership coverage that is only exercised through a freezer fixture (`dashboard-sync`). Mitigation: port those cases to pantry fixtures before deleting.
- **Sync-adjacent PRs.** Changes under `src/hooks`, `src/lib/sync` and `src/lib/supabase` need separate reviewed PRs per the spec.

## 7. Proposed Work Breakdown (each a normal PR unless noted)

0. Stage 0, readiness (no code): run the checks in section 8 (zero lots and zero unmigrated users means no batch migration is needed), compare migration content, take a backup, soak on Preview. Owner-gated.
1. Stage 1, activation: set the Production environment variable and redeploy (owner action, recorded on #700); monitoring notes.
2. Port freezer-based sync and ownership test fixtures to pantry fixtures; keep the legacy-migration tests (they cover the bridge).
3. Dashboard and routes: remove the `PANTRYBOT_PANTRY_ENABLED` flag and its checks (page, pantry, dashboard, AI-plan and barcode routes), remove flag-off branches, Freezer UI and state, the Freezer summary and modal, `localStorage` freezer reads (keep the bridge readers). Route handlers stop passing `freezerInventory`.
4. API and sync (separately reviewed): `/api/freezer` per decision 5; Freezer fields in `/api/sync`, `useUserSync` and `sync/queue` per decision 6; remove the `api-freezer-write` rate-limit key when the route goes.
5. Matching and plan logic: remove `freezerIngredientIds` and the "From Virtual Freezer" copy in the matcher and scoring (pantry mode already ignores them).
6. Storage (local fallback): stop writing the SQLite `freezer_inventory` table; keep reads needed by the bridge.
7. Documentation: OpenAPI (deprecation or removal), terms and privacy wording, README, wiki, `docs/code-review.md` note, `AccountModal` copy, release notes.
8. Stage 3 (later, own plan): drop the bridge, triggers and tables after the retention window.

## 8. Owner-Run Readiness Checks (Production, Aggregates Only)

Run in the Supabase SQL editor; they return counts only.

```sql
select
  (select count(*) from public.users) as users,
  (select count(*) from public.user_freezer_items) as freezer_rows,
  (select count(distinct user_id) from public.user_freezer_items) as users_with_freezer_rows,
  (select count(*) from public.user_pantry_migrations) as migrated_users,
  (select count(*) from public.user_pantry_entries) as pantry_entries,
  (select count(distinct f.user_id) from public.user_freezer_items f
     where not exists (select 1 from public.user_pantry_migrations m where m.user_id = f.user_id)) as unmigrated_users_with_lots;
```

Also confirm the applied migration content matches the repo files for the pantry migrations, that a backup or point-in-time restore point exists, and that a signed-in test account on Preview completes the migration, an offline edit and a reconnect.

## 9. Proposed Acceptance Criteria

- Readiness checks recorded on #700; Production runs with the pantry flag on; migration error rate and unmigrated-user count reviewed after the soak.
- The legacy Freezer UI, flag-off paths, `/api/freezer` handling and Freezer sync fields are gone or deprecated per decisions 5 and 6; sync-adjacent changes shipped as separate reviewed PRs.
- Zero-key guest behavior, sync, ownership, export and delete behave as before for all remaining data, with ported tests; no loss of pantry or sync coverage.
- Original lots remain archived and exportable; nothing is deleted from storage in this prerequisite.
- OpenAPI, terms, privacy text, README and wiki updated; the 43 documentation mentions reviewed.
- `MealPrepDashboard` has no flag-off branch when M3 Phase A starts.

## 10. Dependencies and Open Decisions

Each has a recommendation; none is decided yet. Suggested order of settling is the order listed.

1. **Staging.** **Decided 2026-11-12 (owner): (a), four stages.** Options: (a) four stages as in section 3, with storage dropped later; (b) activation and full removal in one release; (c) never drop storage. **Recommendation: (a).** Activation is reversible only until users migrate, and storage deletion is irreversible, so each deserves its own gate.
2. **Production activation gate and timing.** **Decided 2026-11-12 (owner): activate once v1.6.2 is released, before v1.7, keeping the Stage 0 gates (readiness checks, Preview soak, backup).** This replaces the recommendation below, which proposed the release after v1.7. Consequence: v1.7 ships with Pantry already live in Production, so its sign-in-for-AI work is verified against the pantry-enabled app, and the soak runs alongside v1.7 development. Original options and recommendation for the record. Options: (a) activate after Stage 0 readiness, a Preview soak and a backup, in the next release after v1.7; (b) activate immediately; (c) activate together with the v2.0 release. **Recommendation: (a).** It gives migrations a full release cycle to run lazily before code removal.
3. **Existing Production lots.** **Decided 2026-11-12 (owner): (b), a server-side batch migration, on the owner's understanding that no Production user has existing inventory.** That belief is verified, not assumed: the section 8 query's `users_with_freezer_rows` and `unmigrated_users_with_lots` must be read first. If both are zero, no batch job is written, nothing needs migrating on the server, and decision 4's retention window can shrink to the owner's choice. If either is above zero, a batch script is written as a separate, reviewed PR (it runs outside the client's catalog matching and pending-queue checks, so it must reuse the migration function's exact comparison and be run first on a test account) and run only with the owner's go-ahead. Device-local guest data cannot be batch-migrated from the server and keeps migrating lazily on the device through the retained bridge. Original options and recommendation for the record. Options: (a) rely on lazy per-user migration, keep the legacy table and bridge through a retention window, and review the unmigrated report before any deletion; (b) run a server-side batch migration for every user; (c) leave unmigrated users' lots archived and unshown. **Recommendation: (a)**, adding (b) only if the unmigrated count is material. A batch job bypasses the client's catalog matching and pending-queue checks, and runs against the single shared database.
4. **Retention window before Stage 3.** **Decided 2026-11-12 (owner): a shorter window than the recommendation: one release after activation, provided the section 8 report shows zero users with lots and zero unmigrated users.** If the report shows any, the window reverts to option (a) (at least two releases and a clean report). Stage 3 stays a separate plan and PR either way. Original options and recommendation for the record. Options: (a) at least two releases after activation and a clean unmigrated report; (b) a fixed date such as 90 days; (c) indefinite. **Recommendation: (a)**, with the owner choosing the report threshold (for example zero users with lots, or accept a stated residual).
5. **`/api/freezer` handling.** **Decided 2026-11-12 (owner): (a).** Options: (a) keep the route but return `410 Gone` with an explanatory body for at least one release and mark the operations deprecated in OpenAPI, then remove; (b) delete immediately; (c) keep read-only. **Recommendation: (a).** The route is documented and public; an explicit status is easier for integrators than a 404.
6. **Freezer fields in `/api/sync` and the offline queue.** **Decided 2026-11-12 (owner): (a).** Options: (a) reject Freezer fields from older clients with a clear upgrade error so queued data stays retryable and is never acknowledged; (b) accept and silently ignore them; (c) keep processing them. **Recommendation: (a).** It matches the guardrail that a failure must not acknowledge pending data, and the database fence already rejects migrated users' legacy writes.
7. **The flag itself.** **Decided 2026-11-12 (owner): (b), delete `PANTRYBOT_PANTRY_ENABLED` and its checks together with the Stage 2 code.** The flag therefore works as a kill switch only during the Stage 1 soak (an environment change, valid before users migrate); once the Stage 2 code ships there is no flag-off path and rollback is forward-fix. Consequences: `src/app/page.tsx`, `/api/pantry`, `/api/dashboard`, `/api/ai-meal-plan` and the barcode routes lose their flag checks (the barcode and camera flags remain, and barcode lookup keeps depending on pantry being available), and the environment documentation is updated. Original options and recommendation for the record. Options: (a) keep `PANTRYBOT_PANTRY_ENABLED` for one release after activation (a kill switch only valid before any user migrates, otherwise forward-fix), then delete the flag and its checks; (b) delete the flag with the Stage 2 code; (c) keep it permanently. **Recommendation: (a).** Documents the limited rollback honestly and removes the flag before M3.
8. **Dropped Freezer value features.** **Decided 2026-11-12 (owner): (a), accept section 5.** Options: (a) accept section 5: no banked-savings tracking, lots become available entries, the data stays archived and exportable; (b) preserve cost-basis tracking inside Pantry first; (c) keep a read-only "past savings" view. **Recommendation: (a)**, consistent with the Pantry design (yes/no, no required inputs) and with your retirement decision.
9. **PR slicing and ordering.** **Decided 2026-11-12 (owner): (a).** Options: (a) as in section 7, with the sync-adjacent PRs separate, and the dashboard removal (item 3) landing before M3 Phase A; (b) one large PR. **Recommendation: (a).**
10. **Keyless and local mode.** **Decided 2026-11-12 (owner): (a).** Options: (a) verify guest Pantry works with no Supabase and no flag in the local SQLite fallback path before Stage 2 and add a smoke test; (b) assume it works. **Recommendation: (a).** The flag-off path is today's keyless default, so removing it must prove that the pantry path works keyless.

All 10 decisions are resolved. Remaining before this plan can be approved: the owner-run readiness checks in section 8 (they also settle decisions 3 and 4) and owner review of this plan as a whole.

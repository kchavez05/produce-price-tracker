## 1. Purpose and Scope

Split the `MealPrepDashboard` (3,614 lines on 2026-11-13; 4,164 when this plan was first written) into the Shop, Pantry and Plan modules named in the spec, without changing behavior. M3 is a refactor: same markup, same data, same sync and ownership behavior, same keyless fallbacks. It restyles nothing (M4), adds no primitives (M1) and builds no test stack (M2); it uses all three.

In scope:

- Extract the dashboard's shared state, effects and handlers into hooks and a shared provider.
- Extract the header, modals and the four tab sections into module components.
- Introduce the `/shop`, `/pantry` and `/plan` routes, with `/` opening the last-used module (default Shop), once extraction is complete.
- Keep the old and new structure testable at every step (section 8).

Out of scope:

- Any visual or interaction change, new navigation chrome (tab bar, sidebar, avatar menu: M4), onboarding, the Settings screen, and the Trip enhancements the spec defers.
- Changes to `usePantry`, `useUserSync`, `src/lib/sync`, `src/lib/pantry` or ownership logic. The spec requires such changes to ship as separate, reviewed PRs; M3 consumes them unchanged.
- Retiring the legacy Freezer (decided 2026-11-12, decision 4). M3 assumes it is already gone; the retirement is a prerequisite with its own issue (section 7, item 0b, and decision 14).
- Removing the bring-your-own-key AI input (v1.7 does that; decision 11).

## 2. Baseline (develop at `676b042`, re-surveyed 2026-11-13)

Re-surveyed after v1.6.3 retired the Freezer; the original survey (develop at `7ca88c4`, 2026-11-12) found 4,164 lines, two modes and seven storage keys. The full inventory is in the [characterization map](./v2.0-m3-characterization-map.md). Line numbers drift as v1.7 lands (v1.7 deletes the key modal). Re-survey at the start of implementation.

- **One component.** `src/components/MealPrepDashboard.tsx` is 3,614 lines and the only user of most of its logic. It is a single client component with 40 `useState` calls, 4 refs, 2 effects, 9 memos, 1 callback, and roughly 30 handlers and render helpers. Its default export is imported by `src/app/page.tsx` and by two test files.
- **Rough anatomy:** props and state, lines 94 to 158; cloud hydration, `useUserSync`, `usePantry` and ownership refs, 160 to 197; derived data, 199 to 227; a mount effect that restores five `localStorage` keys, 229 to 290 (carries the file's only `eslint-disable` for `react-hooks/exhaustive-deps`); persistence and mutation handlers (coupons, checklist, preferences, stores, servings, pins, on-hand, saved recipes, AI plan, ZIP, alerts), 292 to 687; more derived data (filtered commodities, meal trio, shopping plan, coupon items), 689 to 840; render helpers, 842 to 920; JSX from 922.
- **JSX regions:** header, account modal and Virtual Pantry panel, 925 to 1181; ZIP, stores, alerts and key modals, 1193 to 1523; tab strip, 1524 to 1599; then `<main>` with four tab sections: Board (514 lines), Meal Plan (581), Shopping List (566, including the print slip) and Radar (346).
- **Module mapping (flows document, section 1):** Shop = Board, Shopping List (Trip view) and Radar; Plan = Meal Plan; Pantry = the Virtual Pantry panel; location, stores, preferences, account and alerts are cross-cutting. The wireframes draw Radar under Shop (`ShopRadar.dc.html`).
- **One mode.** The `pantryEnabled` flag and the legacy Freezer are gone; `usePantry(true, ...)` is hard-wired and on-hand ingredients always come from the private Pantry. M3 starts on one code path.
- **Data flow.** `src/app/page.tsx` builds one `DashboardPayload` on the server (`buildDashboardPayload`), passes it as `initialData`, and the client refetches `/api/dashboard` with all filters as query parameters (`syncDashboard`, nine positional arguments) after ZIP, store, pin, serving and preference changes. Responses are discarded when pantry ownership changed in flight (`pantryOwnerRef`).
- **Sync and ownership.** `useUserSync` (372 lines) and `usePantry` (314 lines) are created inside the dashboard. `handleCloudHydrated` writes cloud preferences into about a dozen local states. The account id for pantry ownership is derived from `userSync.lastSyncedIso` and `initialAccountId`.
- **Tests that mount the dashboard today.** Contrary to the spec baseline ("no tests for `MealPrepDashboard`"), two Tier 3 jsdom files do: `tests/regression/frontend/dashboard-sync.test.ts` (4 tests: reconnect after offline freezer deletion, pins and servings preserved across acknowledgment, offline guest import through reconnect replay, failed guest enqueue retried once) and `tests/regression/frontend/pantry-plan-refresh.test.ts` (2 tests: plan cleared when availability changes without a new AI request, plan retained on quantity or date change). They are valuable, narrow (sync and ownership), and import the default export by path. There are no other dashboard UI tests, and no browser, visual or accessibility tests until M2 is implemented.
- **Dependencies for M3 on other work:** M2 implementation (smoke journeys and baselines) must exist first; v1.7 must have shipped (key modal removed, sign-in prompts added); M1 is not required because M3 changes no styling.

## 3. Target Architecture

```
src/app/
  (app)/layout.tsx        server: loads inventory + initial payload once
  (app)/shop/page.tsx     Shop module
  (app)/pantry/page.tsx   Pantry module
  (app)/plan/page.tsx     Plan module
  page.tsx                `/` opens the last-used module (default Shop)
src/modules/
  shell/    AppProvider, header, modals (ZIP, stores, alerts, account), nav
  shop/     Board, Trip (shopping list), Radar, deal and store badges
  pantry/   Pantry and legacy Freezer panels
  plan/     Dishes, AI chef, saved recipes, preferences
src/modules/*/hooks   state and handlers, DOM-free where practical
```

- **One provider, many routes.** The shared state (ZIP, active stores, preferences, pins, on-hand, servings, the dashboard payload, `useUserSync`, `usePantry`) lives in one client `AppProvider` mounted in the route-group layout. Next.js layouts persist across client navigations, so switching module keeps state, in-flight sync and queued changes intact. This is the main reason route splitting cannot be a simple "one component per page".
- **Context plus custom hooks, no new dependency.** The provider exposes narrow hooks (`useLocation`, `usePreferences`, `useDashboardData`, `usePantryContext`), so modules subscribe to what they use and native code can later reuse the same hooks.
- **Pure logic stays in `src/lib`.** Handlers become hooks that call the existing `src/lib` functions; no pricing, scoring or matching logic moves or changes.
- **Hydration safety preserved.** The `localStorage` restore stays in a post-mount effect inside the provider, so server and first client render still match (a `docs/code-review.md` rule).
- **Server data.** M3 keeps the single payload and the existing `/api/dashboard` contract (decision 5). Per-route loaders are a later optimization.

## 4. Approach: Two Phases

**Phase A, extract in place (URL unchanged).** `/` still renders the same four tabs from the same component tree, but `MealPrepDashboard` shrinks into a thin composition of extracted pieces. Markup and class names are moved verbatim. This phase is verifiable by exact comparison: the rendered HTML before and after each PR must be identical for a set of states (section 8).

**Phase B, split into routes.** Move the provider into a layout, add `/shop`, `/pantry` and `/plan`, make `/` a redirect, and change the temporary tab strip into links. Phase B necessarily changes URLs and navigation behavior, so the characterization suite is edited only where routes require it (M2 decision 13), through its page-object layer.

Order inside Phase A (leaf first, so each PR is small and reversible):

1. Pure helpers and badges (deal, store, cycle-signal badges; formatters).
2. Modals (stores, ZIP, alerts, print slip, key modal until v1.7 removes it, account wrapper).
3. Radar section, then Shopping List (Trip), then Meal Plan, then Board.
4. Header and filters.
5. State: preferences and location hooks, then payload and `syncDashboard` hook, then cloud hydration and pantry wiring.
6. The mount effect and the single `eslint-disable` (decision 3).

Guideline for PR size: move at most about 600 lines per PR, with no logic edits mixed into a move.

## 5. Behavior That Must Not Change

These are the contract M3 PRs are reviewed against, in addition to the `AGENTS.md` review focus:

- **Ownership and sync:** guest data stays private to the device and account; a cloud error never acknowledges a pending change; queued changes stay bound to the account that created them; `syncDashboard` responses are dropped when ownership changed in flight; pantry and sync hooks are consumed unchanged.
- **Keyless behavior:** the app works with no API keys and no Supabase; deterministic fallbacks intact.
- **Pantry mode:** the pantry-enabled path (the only one left after the Freezer retirement) produces today's results.
- **Persistence:** the five `localStorage` keys keep their names, formats and restore order, and the first render stays hydration-safe.
- **Pricing and math:** division-by-zero guards, unit-price normalization and the "Buy 2: Prep 1, Freeze 1" arbitrage math are untouched.
- **Server-funded AI:** requests keep the same authentication behavior.

## 6. Risks

- **Stale closures and ordering.** `syncDashboard` takes nine positional arguments with defaults read from the current render; the mount effect deliberately runs once with an `eslint-disable`. Moving these into hooks can silently change which values a callback sees. Mitigation: extract state last (Phase A step 5), keep argument semantics identical, add a test per moved callback, and run the existing sync regressions on every PR.
- **State lost on navigation.** If the provider is placed below the route boundary, module switches would reset pins, servings or in-flight sync. Mitigation: layout-level provider, plus a browser test that switches modules mid-edit.
- **Retirement sequencing.** Resolved: the Freezer retirement shipped in v1.6.3 and the dashboard has one code path (section 2).
- **Moving target.** v1.6.2 and v1.7 change this file. Mitigation: M3 starts only after v1.7; re-survey first.
- **Test edits hiding behavior changes.** Mitigation: M2 decision 13 (frozen suite; edits explained in the PR) and the DOM-equivalence guard (decision 8).
- **Review fatigue on large moves.** Mitigation: verbatim moves, size limit, a "moved, not edited" PR checklist, and `git diff --color-moved` guidance in `docs/code-review.md`.
- **Native reuse temptation.** Over-abstracting hooks for React Native now. Mitigation: only keep hooks DOM-free where it is free to do so; the v2.1 extraction is separate.

## 8. Test Strategy (Builds on M2)

- **Existing:** the six sync and plan jsdom tests run on every PR, unchanged. Their import path for the default export is kept as a re-export until Phase B, then updated explicitly.
- **M2 characterization suite:** the browser smoke journeys and visual baselines are the behavior contract; Phase A PRs change neither tests nor baselines. In Phase B, locators go through the page-object layer so a route change edits one file.
- **DOM-equivalence guard (new, Tier 1):** serialize the rendered dashboard to HTML for a small set of fixed states (guest default, signed-in, each tab; plus flag off only if the legacy path still exists) and compare to committed goldens. During Phase A any diff means a markup change and fails. Goldens are generated by one command and reviewed like snapshots. They are removed when Phase B changes the structure on purpose.
- **Component tests for moved hooks** use the M1 `tests/helpers/render.ts`, with an axe check on extracted sections.
- **Tiers:** Phase A PRs run Tier 1 and Tier 2 (including browser smoke); a `run-tier3` label (M2 decision 10) is required for the sync-adjacent PRs and for Phase B.

## 9. Proposed Acceptance Criteria

- `MealPrepDashboard` is a composition under about 400 lines; no extracted file exceeds about 600 lines.
- Shop, Pantry and Plan modules exist under `src/modules/`, each rendering independently from the shared provider.
- `/shop`, `/pantry` and `/plan` work as routes; `/` opens the last-used module and defaults to Shop; state survives module switches.
- All six existing jsdom tests, the M2 smoke and visual suites and the DOM-equivalence guard pass; Phase A changed no goldens or baselines; Phase B edits are limited to routes and locators and are explained.
- Sync, ownership, pricing, scoring and keyless behavior are unchanged, with the same `localStorage` keys (minus the retired Freezer keys, removed by the prerequisite).
- No new runtime dependency; no `any`; no new `eslint-disable`; the existing one removed or justified per decision 3.
- Documentation and the spec milestone table updated.

## 10. Dependencies and Open Decisions

Each has a recommendation; none is decided yet. Suggested order of settling is the order listed.

1. **Refactor strategy.** **Decided 2026-11-12 (owner): (a), two phases.** Options: (a) two phases: extract in place with the URL unchanged, then split into routes; (b) split into routes first and move code as pages are built; (c) rewrite each module fresh and swap. **Recommendation: (a).** It keeps every PR verifiable by exact DOM comparison and keeps `/` working throughout; (b) mixes behavior change with code moves, and (c) has the highest regression risk for sync and ownership.
2. **Where shared state lives.** **Decided 2026-11-12 (owner): (a).** Options: (a) a layout-level provider with narrow context hooks, no new dependency; (b) a state library (for example Zustand); (c) keep one big state hook passed down as props. **Recommendation: (a).** No dependency to approve, state survives route changes, and hooks can later be reused by React Native.
3. **The mount effect and its `eslint-disable`.** **Decided 2026-11-12 (owner): (a).** Options: (a) move it verbatim into the provider and resolve the lint suppression in a separate, reviewed PR after extraction; (b) resolve it during the move; (c) leave it. **Recommendation: (a).** It restores five storage keys and triggers a dashboard refetch, so changing its dependency semantics belongs in its own PR that `AGENTS.md` guardrails ask for, not inside a move.
4. **Legacy Freezer mode.** **Decided 2026-11-12 (owner): drop it.** The consequences are not a refactor, so the retirement is split out as decision 14 and is a prerequisite for M3 rather than a step inside it. The original options and recommendation follow for the record. Options: (a) preserve both the pantry-flag-on and legacy Freezer paths through M3 and decide removal separately; (b) require the flag on in v2.0 and delete the legacy path in M3; (c) delete it before M3. **Recommendation: (a).** Behavior-preserving is the point of M3; removal is a product decision with its own migration and test cost. The owner should say whether the legacy path is expected to survive v2.0.
5. **Server data per route.** **Decided 2026-11-12 (owner): (a).** Options: (a) keep one payload loaded in the layout and the `/api/dashboard` contract unchanged; (b) per-module loaders now. **Recommendation: (a).** Per-route loading is an optimization with caching and ownership implications; do it after M4 if needed.
6. **Module and file layout.** **Decided 2026-11-12 (owner): (a).** Options: (a) `src/modules/{shell,shop,pantry,plan}` with `hooks` beside components; (b) keep everything in `src/components` subfolders; (c) `src/features`. **Recommendation: (a)**, because the module names match the spec and a v2.1 monorepo extraction can lift hooks and logic by folder.
7. **Extraction order and PR size.** **Decided 2026-11-12 (owner): (a).** Options: (a) leaf first as in section 4, about 600 lines per PR; (b) top down (shell first). **Recommendation: (a).**
8. **DOM-equivalence guard.** **Decided 2026-11-12 (owner): (a).** Options: (a) add the golden-HTML Tier 1 test for Phase A; (b) rely on the M2 visual baselines and existing tests only. **Recommendation: (a).** Visual baselines catch layout, not attribute, label or order changes; a golden-HTML check is cheap, runs in Tier 1 and is the strongest evidence that moves were verbatim.
9. **Phase B navigation.** **Decided 2026-11-12 (owner): (a).** Options: (a) a temporary tab strip rendered as links, replaced by the M1 TabBar and Sidebar in M4; (b) build the final tab bar and sidebar in M3. **Recommendation: (a).** Final navigation is a visual and interaction change that belongs in M4 with the redesign.
10. **`/` redirect and last-used module storage.** **Decided 2026-11-12 (owner): (a), a cookie.** Options: (a) a cookie so the server can redirect without a flash; (b) `localStorage` read after mount (no redirect, flash); (c) always Shop. **Recommendation: (a)**, with guest-safe defaults and no personal data in the cookie (module name only). Needs a short spike on caching behavior with `force-dynamic`.
11. **BYOK key modal and v1.7.** **Decided 2026-11-12 (owner): (a).** Options: (a) start M3 after v1.7 removes it, so no dead code is extracted; (b) extract it and delete it later. **Recommendation: (a)**, consistent with the release parent's ordering.
12. **Radar placement.** **Decided 2026-11-12 (owner): (a).** Options: (a) a Shop section as in the wireframes; (b) its own destination. **Recommendation: (a).**
13. **Timing and parallelism.** **Decided 2026-11-12 (owner): (a).** Options: (a) start Phase A after M2's smoke journeys and baselines are merged, run Phase B after M1's tokens and primitives (so M4 can follow immediately); (b) start M3 after M2 and M1 both finish; (c) start now. **Recommendation: (a).** M3 needs the safety net from M2, not the styling from M1.

14. **Freezer retirement: scope, sequencing and the Production flag.** New, raised by decision 4. **Decided 2026-11-12 (owner): (a), a separate prerequisite completed before M3 Phase A, tracked in [#700](https://github.com/kchavez05/produce-price-tracker/issues/700).** The individual owner calls it needs (Production activation of the pantry flag, treatment of existing Production Freezer lots, API deprecation note) are made in that prerequisite's own plan. Retiring the Freezer means: enabling `PANTRYBOT_PANTRY_ENABLED` in Production (which first needs the pantry migrations verified against the one shared database, an owner-gated step); a user-data decision for existing Freezer lots in Production (the existing migration converts them to pantry entries once); removing `/api/freezer`, the sync payload's `freezerItems`, the weekly digest and AI-plan freezer inputs, and the OpenAPI entries (a public API surface, so a deprecation or version note); and updating terms and privacy text. Options: (a) a separate prerequisite issue and PRs, completed before M3 Phase A, ideally as part of or right after v1.7; (b) fold it into M3 as Phase A step 0; (c) do it after M3, with M3 preserving the two-mode code and isolating the legacy branches. **Recommendation: (a).** It changes behavior, data and a public API, touches sync and ownership code that `AGENTS.md` and the spec require to ship as separate reviewed PRs, and needs owner decisions on Production activation and existing user data. Mixing it into a behavior-preserving refactor would break the M3 safety-net rule (no unexplained test or baseline edits). If v1.7 will not enable the flag in Production, choose (c).

15. **Pins and servings persistence.** **Decided 2026-11-13 (owner): not persisted locally.** Pins and servings stay in state and cloud preferences only, as today; M3 adds no `localStorage` key for them. Raised by the [characterization map](./v2.0-m3-characterization-map.md).
16. **Gap tests location.** **Decided 2026-11-13 (owner): inside the golden-HTML PR.** The jsdom tests for the coverage gaps are written as part of work item 1 rather than a separate prerequisite PR.
17. **Plan baseline.** **Decided 2026-11-13 (owner): update the plan** to the re-surveyed figures in section 2 (this revision).

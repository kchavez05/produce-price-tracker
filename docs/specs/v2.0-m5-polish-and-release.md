## 1. Purpose and Scope

Prove that the redesigned app is accessible, responsive and fast enough to ship, and release it. M4 makes each screen correct; M5 checks the whole app together, sets and enforces a performance budget, finishes the documentation, and runs the v2.0.0 release (`AGENTS.md` Step 6). M5 changes no sync, auth, ownership, pricing, scoring or zero-key behavior, and adds no features.

In scope (spec section 5): the WCAG AA pass, the responsive pass, the performance budget, and release docs. Plus the items M4 hands over: enforcing the zero raw-palette-class target (M4 decision 10), revisiting an automated non-text contrast check (M4 decision 11), confirming the PWA and manifest changes held (M4 decision 12), rerunning the real-device checklist for the release (M4 decision 13), and measuring the long Shop list (M4 decision 15).

Out of scope:

- New product features, and any redesign of a screen beyond fixing defects the passes find. A defect that needs a layout the wireframes do not show goes back to a design decision, not an ad hoc fix.
- Everything M4 decision 16 defers to v2.1 or later: iPhone landscape and Duo posture handling, fold or hinge behavior, pantry amounts, shopping list enhancements, per-route data loaders, Storybook, Android, desktop-specific layouts, native apps, and [#621](https://github.com/kchavez05/produce-price-tracker/issues/621).
- Appium ([#695](https://github.com/kchavez05/produce-price-tracker/issues/695)), LambdaTest real-device runs ([#696](https://github.com/kchavez05/produce-price-tracker/issues/696)), Storybook ([#697](https://github.com/kchavez05/produce-price-tracker/issues/697)) and connected-tier browser tests ([#698](https://github.com/kchavez05/produce-price-tracker/issues/698)). They stay in Backlog (decision 20).
- Any change under `usePantry`, `useUserSync`, `src/lib/sync`, `src/lib/pantry` or ownership code (spec section 6).

## 3. Approach

1. **Audit first, then fix, then lock.** The first M5 PRs add measurement only (a cross-app accessibility sweep, a performance report, a responsive sweep), advisory and with no fixes. Findings become issues sorted by the severity policy (decision 18). Fix PRs follow. The last step turns the checks that passed into blocking gates so v2.0 cannot regress after release.
2. **Evidence over assertion.** Every pass criterion names how it is shown: a CI run, a recorded number, a manual checklist result with date and device, or a documented known issue with a reason. The release notes list evidence and limits explicitly, as v1.6.2 did.
3. **Automated where it is honest, manual where it is not.** Axe cannot judge VoiceOver reading order, meaningful labels, or non-text contrast reliably; WebKit on Linux is not Safari. Manual checks cover those and are run by the owner on the two real devices.
4. **No new runtime dependencies.** Dev dependencies only, and only if a decision approves them (decision 9).
5. **One release, then forward-fix.** UI is the only thing that rolls back; data and API changes already shipped earlier (Freezer retirement) are forward-fix only (decision 19).

## 4. The WCAG AA Pass: Proposed Definition

Standard: WCAG 2.2 Level AA. M2's axe gate uses "WCAG 2.x A and AA"; M5 pins the tag set to include 2.2 (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`; confirm the installed `axe-core` supports the 2.2 tag when M5 starts). The project's own rules are stricter than AA where noted (44 px targets; Title Case headings are a convention, not a WCAG criterion).

| Area | Automated evidence | Manual evidence | Pass means |
|---|---|---|---|
| Rules axe can test (names, roles, contrast of text, landmarks, labels, headings, focus order basics) | axe over every Tier 3 screen and state, both engines, both themes, all matrix widths | none | Zero violations of any impact on redesigned screens and an empty allowlist at release (the end state; the gate starts at serious and critical and moderate or minor findings are triaged first, decisions 3 and 18) |
| Screen reader | none | VoiceOver walk-through of the five flows on iPhone 17 Pro and iPad | Every flow is completable by VoiceOver alone with sensible names, order and announcements; findings recorded |
| Keyboard | Playwright tab-order and focus tests (M2 journey 7, extended) | Hardware keyboard on the iPad once | No keyboard trap; visible focus; Escape closes sheets and returns focus |
| Zoom, text size and reflow (1.4.4, 1.4.10, 1.4.12) | Playwright at 320 CSS px and with enlarged text spacing; viewport meta guard | Safari Text Size and page zoom on both devices | No loss of content or function; no horizontal scroll except data tables or code that need it |
| Motion (2.3.3 is AAA; 2.2.2 is A) | Playwright with `prefers-reduced-motion: reduce` asserts no running animations or transitions | iOS Reduce Motion once | No essential content depends on motion; reduced-motion honored app-wide |
| Color-only cues (1.4.1) | partial: a lint-style review list | Manual review of deal, status and error cues in grayscale | Every state shown by color also has text, icon or shape |
| Non-text contrast (1.4.11) | Token test plus computed-style check (decision 6) | Spot check in dark | Control boundaries and focus rings at least 3:1 in both themes |
| Target size | Playwright bounding-box check, 44 px project rule (WCAG 2.5.8 AA needs 24 px) | none | Every visible interactive element is at least 44 x 44 px, with inline-text links exempt and listed |
| Forced colors and print | Playwright `forcedColors: 'active'` and print emulation screenshots, advisory | Print preview of the shopping slip once | Content stays visible and usable; the slip prints legibly |
| Dark mode | everything above in both themes | spot check on both devices | No pair below its threshold in either theme |

## 5. Behavior That Must Not Change

- Everything in M3 section 5 and M4 section 5: ownership and sync (a cloud error never acknowledges a pending change; queued changes stay bound to their account), zero-key behavior, persistence keys and hydration safety, pricing and unit-price guards, the "Buy 2: Prep 1, Freeze 1" math, authenticated server-funded AI, guest privacy, defaults when onboarding is skipped, nothing required in Pantry, print and forced-colors fallbacks.
- **Pinch zoom stays on.** No M5 fix may add `user-scalable=no` or lower `maximumScale`. A test guards the viewport meta.
- **Performance work is not behavior work.** A budget fix may change how much is rendered or loaded at once (paging, splitting a bundle), never what a price, score or plan result is.
- **Release does not change data.** No migration, no hosted-schema change and no environment change rides in the v2.0.0 release PR.

## 6. Risks

- **Plan drift.** M1 to M4 are unimplemented; names may change. Mitigation: re-survey at the start of M5 and update this document in its tracking PR.
- **Late discovery.** The whole-app passes could find serious defects after M4 declares screens done. Mitigation: audit PRs come first (section 3), the severity policy (decision 18) is settled before they run, and Tier 3 with axe has been running on every M4 screen PR.
- **WebKit on Linux is not Safari.** Mitigation: the manual device pass is a release gate; the notes list what the two devices do not cover.
- **Budget set before measurement.** A number picked now could be unreachable or meaningless. Mitigation: decision 8 sets the metrics and the method now, and the numeric thresholds only after a measured baseline; the one figure on hand (285 kB First Load JS on `/`) is the "before".
- **Flaky performance checks.** Lab metrics vary on shared runners. Mitigation: size budgets (deterministic) block; timing metrics are advisory with a tolerance band until they prove stable (decision 10).
- **Devices not covered.** Owner devices miss the iPad mini, iPhone 17e and Pro Max widths and the Duo. Mitigation: emulated widths in CI (756 and 440 are in or added to the matrix, decision 7) and a stated limit in the notes.
- **Large UI change for existing users.** Shop loses its ZIP and store row; the Freezer is gone. Mitigation: decision 19.
- **Billing.** Private repository. Mitigation: performance and extra sweeps run in the existing Tier 3 job or on the `run-tier3` label, not on every PR.
- **Release evidence thinner than the checklist.** v1.6.2 closed on an attestation. Mitigation: decision 17 defines what the owner checks and what is recorded, and the notes state limits.

## 8. Test Strategy

- **Automated gates after lock-in:** Tier 1 (contrast, ratchet, token checks), Tier 2 smoke with axe on develop PRs, Tier 3 (full matrix, Chromium cross-check, dark mode, snapshots, wide axe sweep). The size budget is deterministic and cheap, so it runs in the existing build job on every PR to `develop` and `main`, not only in Tier 3, so a regression is caught early on `main` PRs or `run-tier3`. The performance timing run is advisory (decision 10).
- **Manual gates:** the owner's device run for the release (decision 14), recorded with device, OS version, date and results in the checklist file and linked from the release notes.
- **No fixed sleeps, fresh context per test, CI-only baselines** (M2 rules apply unchanged).
- **Production check:** an owner-run checklist against pantrybot.dev after the production deployment is Ready (decision 17).

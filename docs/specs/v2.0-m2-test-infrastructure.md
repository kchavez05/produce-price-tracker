# v2.0 M2: Test and Accessibility Infrastructure — Plan

Status: **Approved 2026-11-12 (owner).** Implementation starts once M1 batch 0 merges and v1.7 ships (decision 14). Part of the [v2.0 specification](./v2.0-ui-redesign.md). Tracked in [#694](https://github.com/kchavez05/produce-price-tracker/issues/694), under the v2.0.0 release parent [#682](https://github.com/kchavez05/produce-price-tracker/issues/682). Follows [M1](./v2.0-m1-foundations.md) (issue [#685](https://github.com/kchavez05/produce-price-tracker/issues/685)) and feeds M3 (dashboard decomposition).

## 1. Purpose and Scope

Give v2.0 a browser-level safety net before the dashboard is split (M3) and the screens are redesigned (M4): real-browser smoke tests, accessibility checks inside the browser, visual-regression checks, and the CI tier assignment that runs them.

In scope (per spec section 5): browser smoke and visual checks, CI tier assignment, and updates to `ci.yml`, `AGENTS.md` and `docs/code-review.md`.

Out of scope:

- The shared jsdom helper `tests/helpers/render.ts` and the `axe-core` dev dependency. Decided for M1 (M1 decision 1); M2 reuses them.
- Testing against production or against Vercel Preview deployments (see decision 2).
- Native-app tests (Appium, later), cloud device farms (LambdaTest, later), Android, desktop browsers, iPhone landscape, iPhone Duo posture handling (all deferred by the spec).
- Real-device checks (camera capture, Safari quirks). They stay manual, like the existing real-device verification issues.
- Redesigning any screen. M2 tests the app as it is; M4 re-baselines.

## 2. Baseline (develop at `1a16b0f`, surveyed 2026-11-12)

- Stack: Next.js 15.5, React 19, Tailwind 4.3, Vitest 5.1, jsdom 31. Node 22 in CI.
- **There are currently no browser, visual or accessibility tests.** The only UI tests are jsdom component tests for `VirtualPantry`, `BarcodeEntry` and `BarcodeCamera` (hand-rolled `createRoot` and `act`), plus the smoke flow `tests/smoke/frontend/barcode-pantry-flow.test.ts`, which mounts real components in jsdom. Nothing tests `MealPrepDashboard`, `AccountModal` or the Data Explorer.
- Tiers today are directories under `tests/` run by Vitest (`include: tests/**/*.test.ts`, node environment, 10s timeout): `tests/unit` (Tier 1, every branch and PR), `tests/smoke` (Tier 2, PRs and pushes to `develop`, `main`, `release`), `tests/regression` (Tier 3, PRs and pushes to `main` and `release`). Scripts: `test:unit`, `test:smoke`, `test:regression`, `test:ci:develop`, `test:ci:main`.
- `ci.yml` has one job, `Typecheck, Lint & Build` (10-minute timeout), whose name is the required check for PRs. It runs catalog check, typecheck, lint, tiers, build and a critical-severity audit. There is no Playwright, no browser install and no artifact upload.
- Zero-key behavior: `isSupabaseConfigured()` is false without `NEXT_PUBLIC_SUPABASE_*`, and the app runs as a guest with a local session cookie. Barcode lookup and camera are behind `PANTRYBOT_BARCODE_LOOKUP_ENABLED` and `PANTRYBOT_BARCODE_CAMERA_ENABLED` (read in `src/app/page.tsx`); the Pantry itself is always on since the Freezer retirement in v1.6.3 and has no flag. These are feature flags, not secrets. Barcode lookup in production also needs `PANTRYBOT_BARCODE_SHARED_LIMIT_VERIFIED`, so browser tests that exercise it must stub the HTTP boundary.
- `src/middleware.ts` runs `updateSession` on nearly every request; with Supabase unconfigured it must remain a no-op (verify during the scaffold PR).
- Vercel Preview deployments of `develop` and PR branches are protected by Vercel Authentication, so an unauthenticated runner cannot load them. Previews also carry the project's real environment variables, which conflicts with a keyless test principle.
- The repository is private, so GitHub Actions minutes are billed against the plan's allowance. Every added CI minute counts; this drives the runtime budget in section 7.
- M0 findings relevant here (UI audit and device specs): the homepage is one ~4,100-line client component; pixel metrics at phone width were approximate when emulated; Apple's guidance is to test by width and size class, not device or orientation checks.

## 3. Approach

1. **Playwright Test** for browser tests, running against a production build served by `next start` on the CI runner, with no secrets. Tests live in `tests/e2e/` as `*.spec.ts`, so Vitest's `*.test.ts` include never picks them up and Playwright never picks up Vitest files.
2. **Engines:** WebKit is the primary engine (closest available to the Safari floor: latest two iOS and iPadOS majors). Chromium is added only for the Tier 3 regression pass, as a cheap second opinion. WebKit on a Linux runner is Playwright's WebKit build, not Safari; it catches layout and behavior regressions, not Apple-specific rendering. Real Safari stays a manual release check.
3. **Tiers.** Tier 1 stays Vitest unit. Tier 2 adds a small browser smoke suite on one iPhone and one iPad viewport. Tier 3 adds the full viewport matrix, dark mode (once M1 lands), the visual snapshots and the broader accessibility sweep.
4. **Accessibility inside the browser:** `@axe-core/playwright` on every smoke journey screen, failing on serious and critical WCAG 2.x A and AA violations, with a recorded allowlist of known current violations that M4 and M5 burn down (ratchet, as with M1's palette-class guard).
5. **Visual checks** use Playwright's built-in screenshot comparison with baselines committed to the repo, generated only on the CI Linux image, fonts and animation stabilized.
6. **Deterministic data and time:** guest sessions in a fresh browser context per test, no network except the local server, HTTP-boundary stubs through `page.route`, and a fixed clock.
7. **Separate CI job** (`Browser Tests`) next to the existing job, so the required `Typecheck, Lint & Build` check keeps its name and timing.

## 3a. Future Direction (Backlog, Not M2 Scope)

- **Appium for native apps (v2.x).** Playwright cannot drive native iOS apps, so Appium will be a separate suite when the Expo/React Native apps exist. M2 keeps shared things tool-neutral: test journeys are written as plain-language flows in the spec, accessible names and roles are the locator contract (these also serve as native accessibility labels), and test data stays in plain fixtures.
- **LambdaTest (real browsers and devices), way down the road.** The aim is to run the Tier 3 suite on real Safari and real iOS and iPadOS devices, closing the WebKit-on-Linux gap. To keep that a configuration change rather than a rewrite, `playwright.config.ts` takes its browser target and base URL from environment variables, and no test assumes the local server or a local file path. Provider capabilities, pricing and Playwright support on real iOS devices must be verified when that work is planned; nothing here relies on them.
- **Storybook (decision 12).** A Backlog item to adopt Storybook once the primitive set is large enough to justify it; until then the `/design` route is the style guide.
- Backlog issues: Appium [#695](https://github.com/kchavez05/produce-price-tracker/issues/695), LambdaTest [#696](https://github.com/kchavez05/produce-price-tracker/issues/696), Storybook [#697](https://github.com/kchavez05/produce-price-tracker/issues/697), and connected-tier browser tests [#698](https://github.com/kchavez05/produce-price-tracker/issues/698). None is scheduled.

## 4. Browser Test Tool Comparison

| Option | WebKit | Mobile emulation | Built-in visual and trace | Cost and fit |
|---|---|---|---|---|
| **Playwright Test (recommended)** | Yes (bundled build) | Viewport, DPR, touch, user agent | Screenshot comparison, trace viewer, video | Free, MIT; browsers download on install and cache; TypeScript native; parallel by file |
| Vitest browser mode (with a Playwright provider) | Through the provider | Limited | Experimental visual features | Fits the existing runner, but tests components in isolation, not the built app, routes or cookies; still needs Playwright installed; still maturing |
| Cypress | No (experimental only) | Viewport only | Paid cloud for much of the visual tooling | Cannot run the Safari-like engine the floor requires |
| Puppeteer | No | Chromium only | None built in | Chromium-only; would need extra libraries for everything |
| Selenium or WebdriverIO | Safari only on macOS | Via drivers | Plugins | Heavier setup, slower, macOS runners are billed at a higher multiple |
| Storybook plus a test runner | Via Playwright | Per story | Visual add-ons are mostly paid services | Adds a framework; M1 decision 6 chose no Storybook |

Recommendation: Playwright Test. It is the only option that gives WebKit, mobile emulation, screenshot comparison, accessibility integration and traces in one free dev dependency with no hosted service.

Dev dependencies added in M2: `@playwright/test` and `@axe-core/playwright` (the latter depends on `axe-core`, which M1 already adds, so they should resolve to the same copy). Both pinned to exact versions at implementation time, matching how this repo pins `vitest` and `jsdom`. No runtime dependency changes.

## 5. Tier Assignment

| Tier | Runner | Runs on | Contents |
|---|---|---|---|
| 1 Unit | Vitest | every branch and PR (unchanged) | logic, jsdom components, M1 axe component checks, token contrast |
| 2 Smoke | Vitest and Playwright | PRs and pushes to `develop`, `main`, `release` | existing Vitest smoke, plus **browser smoke**: WebKit, iPhone 390x844 and iPad 820x1180 portrait, about 6 to 8 journeys, axe on each screen, no screenshots |
| 3 Regression | Vitest and Playwright | PRs and pushes to `main`, `release` | existing Vitest regression, plus the **full viewport matrix**, Chromium cross-check, dark mode, **visual snapshots** and the wider axe sweep |

Scripts (proposed): `test:e2e:smoke`, `test:e2e:regression`, `test:e2e:update` (regenerate baselines), plus `test:ci:develop` and `test:ci:main` left Vitest-only so they stay runnable without browsers.

Smoke journeys (first cut, keyless guest, flags on in the test server):

1. `/` loads, shows the header, ZIP, and a price list with no console errors or hydration warnings.
2. Change ZIP and store filter; list updates.
3. Open Virtual Pantry, add an item by typed entry (barcode HTTP stubbed), see it in the list; reload and it persists as a guest.
4. Open and close the account modal; guest state remains; no sign-in is attempted.
5. Meal plan: generate the deterministic keyless plan; shopping list and cart export render.
6. Static pages `/privacy`, `/terms`, `/docs`, `/data` load.
7. Keyboard pass: tab order reaches the main controls; modal focus stays inside and Escape returns focus (guards the focus rules M1 builds).

## 6. Visual Snapshots

- **Tooling:** Playwright `toHaveScreenshot`. No third-party service (Percy, Chromatic and similar are paid or hosted and would receive app screenshots).
- **Baseline storage:** committed PNGs next to the specs (`tests/e2e/**-snapshots/`), one folder per project. Rendering differs by OS, so baselines are generated only by CI on `ubuntu-latest` and are never accepted from a developer machine. A `workflow_dispatch` job (or a PR label) runs `test:e2e:update` and uploads the new images as an artifact for a human to commit; the repo is never auto-committed to.
- **Size:** about 20 to 30 snapshots at roughly 50 to 150 KB each, so a few megabytes, growing with each M4 re-baseline. Git history keeps old versions; revisit LFS or an artifact-only store only if the folder passes about 25 MB.
- **Tolerance:** `maxDiffPixelRatio` of 0.01 with Playwright's default per-pixel threshold, animations disabled, caret hidden, clock fixed, fonts left as the system stack (so the Linux runner's fallback font is the baseline, not SF). The visual check guards layout and spacing, not Apple font fidelity.
- **What is captured:** Shop home, Pantry empty and with items, Plan, account modal, and Data Explorer, at iPhone 390 and iPad 820 portrait, light only until M1 ships dark mode. Dynamic content (prices, dates) comes from the deterministic fixtures or is masked.
- **Role:** M3 is behavior-preserving, so any snapshot diff in an M3 PR is a failure to explain or fix. M4 changes the UI on purpose; each M4 screen PR re-baselines its own snapshots.
- **Rollout:** advisory first (reported, not blocking) for the first two weeks of green runs, then blocking on Tier 3.

## 7. Matrix, Runtime and Flake Budget

Viewport matrix (CSS px, from the Apple device specs; DPR and touch set per class):

| Name | Size | Tier |
|---|---|---|
| iPhone compact | 390x844 | 2 and 3 |
| iPhone Pro | 402x874 | 3 |
| iPhone Pro Max | 440x956 | 3 |
| iPad portrait | 820x1180 | 2 and 3 |
| iPad landscape | 1194x834 | 3 |
| iPhone Duo inner (width check only, no posture) | 626x890 | 3 |

iPhone landscape is not tested (decided 2026-11-12). Tests assert by width class and behavior (tab bar versus sidebar, no horizontal scroll), not by model.

Budgets (proposed, to be confirmed after the scaffold PR measures real numbers):

- Tier 2 browser job: at most 4 minutes wall clock, including install from cache. Tier 3 browser job: at most 10 minutes.
- Cache the Playwright browsers keyed on the Playwright version, and install WebKit only for Tier 2 (Chromium added for Tier 3).
- Workers: 2. Retries: 0 locally, 1 in CI with a trace on first retry. A test that passes only on retry is reported and fixed within a week or quarantined with an issue; quarantined tests are listed in the spec, never silently skipped.
- No fixed sleeps; web-first assertions only. Every test gets a fresh browser context.
- Billing: private repository, so estimate monthly minutes after the first two weeks and report them to the owner.

## 8. Test Data, Flags and Reaching a Server

- **Server:** `playwright.config.ts` starts `next start` through `webServer` after `next build`, with no Supabase, Gemini, USDA or Kroger variables. CI reuses the build already produced by the existing job only if artifacts are shared; otherwise the browser job builds once itself (about the same cost as today's build step).
- **Flags:** the test server sets `PANTRYBOT_BARCODE_LOOKUP_ENABLED=true`, and a camera flag only if a journey needs it (camera capture stays in jsdom, since WebKit has no fake media device flag). These are on/off switches, not secrets.
- **Guest mode:** every test starts from a clean context, which creates a private guest session through the normal cookie. Tests never log in, never call Supabase, and fail if any request leaves `localhost`.
- **Market data:** the keyless deterministic baseline (and `data/` fixtures) provides prices; the scaffold PR confirms nothing on `/` needs a network call in CI. A feasibility spike on 2026-11-13 ([#694 comment](https://github.com/kchavez05/produce-price-tracker/issues/694#issuecomment-6865844622)) confirmed no request left localhost.
- **Vercel Analytics stub:** `src/app/layout.tsx` loads `@vercel/analytics`, which requests `/_vercel/insights/script.js`. That 404s on a local `next start` and logs a console error on every page. The support layer stubs `**/_vercel/insights/**` with an empty 200 response, so the "no console errors" journey stays strict and the request is not in the network guard's allowance.
- **Known issues at the baseline (current UI, measured in the spike):** at 390x844 the header's top-right control row reaches 551 px, so the page scrolls horizontally (unconfirmed on a device; the M0 audit reported none); `/` has two serious axe violations at both widths: `color-contrast` (about 60 nodes) and `select-name` (1 node). Both are recorded as allowlist entries (decision 15), not fixed in M2 or M3.
- **Preview deployments:** not used in M2 (decision 2).
- **Ownership checks:** a smoke journey asserts that a second context does not see the first context's pantry (guards the session-isolation rule in `AGENTS.md`).

## 9. How M3 Uses This

- Before M3 starts, the smoke journeys and the baseline snapshots are the **characterization suite** for the dashboard: they capture today's behavior and layout on the current monolith.
- M3 PRs must keep the suite green with **no baseline changes and no test edits**, other than the route and locator changes the split itself requires (`/` to `/shop`, `/pantry`, `/plan`).
- To keep those edits small, tests use role and label locators through a small page-object layer in `tests/e2e/support/`, so a route move touches one file.
- Any M3 PR that needs a test or baseline change says why in its description; reviewers treat that as a behavior-change flag (the existing `docs/code-review.md` focus on sync, ownership and zero-key behavior still applies).

## 12. Proposed Acceptance Criteria

- `npm run test:e2e:smoke` runs locally and in CI against a keyless production build, with no secrets, and passes in WebKit at 390x844 and 820x1180.
- Tier 2 and Tier 3 browser suites run on the PR types in section 5; the required `Typecheck, Lint & Build` check is unchanged.
- Every smoke screen runs axe, with zero new serious or critical violations and a recorded allowlist for known ones.
- Visual baselines exist for the screens in section 6, regenerated only by CI, and Tier 3 fails on an unexplained diff.
- Tier 2 browser job is within its runtime budget; flake rate is recorded for two weeks of runs and no unexplained retries remain.
- `AGENTS.md`, `docs/code-review.md`, README and wiki describe the tiers, commands, snapshot update process and rules.
- The characterization map for M3 is written and agreed.
- No change to sync, auth, pricing, scoring or zero-key behavior; no new required environment variable.

## 13. Risks

- **WebKit on Linux is not Safari.** Mitigation: use it for behavior and layout only; keep a short manual iOS and iPadOS Safari checklist in each release.
- **Flaky visual tests** from fonts, animation and dynamic data: fixed clock, deterministic data, CI-only baselines, advisory first.
- **Billing growth** on a private repository: cached browsers, Tier 2 kept small, measure after two weeks.
- **Baseline churn** in M4: expected; each screen PR re-baselines and says so.
- **Existing accessibility violations** would block everything on day one: handled with the allowlist ratchet.
- **Vitest and Playwright collisions** (globs, `tsc` including `tests/`): separate `*.spec.ts` extension and directory, checked in the scaffold PR.
- **Next.js build duplicated** in the browser job: share the build as an artifact if the minutes matter.

## 14. Dependencies and Open Decisions

1. **Browser test tool.** Options: (a) Playwright Test; (b) Vitest browser mode; (c) Cypress. **Decided 2026-11-12 (owner): (a), Playwright Test.** Adds `@playwright/test` and `@axe-core/playwright` as dev dependencies, pinned exactly. Direction recorded with the decision: Appium for native mobile testing is expected later (v2.x native apps), and a LambdaTest integration (real Safari and real iOS devices) is a backlog effort well after v2.0. Neither is M2 scope; M2 only avoids closing the door on them (see section 3a).
2. **What the browser tests run against, and Vercel Preview access.** **Decided 2026-11-12 (owner): (a), a keyless local build; connected tier (d) stays in Backlog; no Vercel Preview testing and no production-synced database.** Options: (a) a local production build on the CI runner, keyless; (b) Vercel Preview with a protection-bypass secret (`x-vercel-protection-bypass` header, stored as a GitHub secret); (c) both, with previews as a post-deploy probe; (d) a local build connected to a throwaway Postgres or local Supabase seeded from the migrations. **Recommendation: (a) for M2**, with (d) as a Backlog "connected tier" if signed-in browser flows are wanted later. Copying production would put real users' pantry and account data on runners and laptops (privacy and GDPR exposure) and make tests depend on changing data, which defeats deterministic snapshots. If connected flows are needed, seed a disposable database from `supabase/migrations/` with synthetic fixtures (the repo already runs those migrations in PGlite for unit tests, and the Supabase CLI can run a local stack in Docker), reset per run, never synced from production. A separate hosted staging Supabase project is the other route, and is an owner cost and secrets decision.

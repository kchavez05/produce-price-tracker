# Virtual Pantry implementation plan

This plan implements the [approved product specification](v1.6.0-virtual-pantry.md). v1.6.0 is not shipped. The package version stays at 1.5.2 until the release workflow.

## Confirmed product decisions

- Pantry staples participate in coverage, shopping needs, and additional grocery costs. Use fixed USD estimates per kitchen unit in v1.6.0. Dynamic staple prices belong to v1.6.2 alongside barcode scanning.
- Purchase suggestions, “Buy 2,” and “I cooked this” do not write inventory. Only an explicit pantry add, availability change, edit, import, or deletion may change it. Remove the existing purchase-suggestion inventory write when switching the dashboard to Virtual Pantry.

## Slice 1: contract, identity, migration preparation, staple estimates

Implemented in `src/types/pantry.ts`, `src/data/pantry-ingredients.ts`, and `src/lib/pantry/`:

- Explicit boolean availability with optional quantity, unit, location, and calendar date. Validation whitelists editable fields and reports individual field errors. Revision and update metadata are reserved for persistence.
- A generic ingredient catalog independent of market offers. Reviewed exact market identities retain their canonical IDs; staple IDs distinguish rice varieties, flour types, and canned versus dried beans. Search aliases do not automatically map custom entries.
- Reasonable fixed estimates such as broth at $0.40/cup, olive oil at $0.20/tbsp, and garlic at $0.08/clove. These estimate recipe-use amounts, not package checkout totals or observed offers. Unsupported units and missing prices produce an incomplete estimate rather than an invented conversion or offer.
- Pure requirement evaluation counts distinct required identities, separates optional ingredients, and omits available ingredients from additional cost without reading optional inventory quantities or dates. This helper is not yet connected to existing recipe blueprints or dashboard totals.
- Pure migration preparation merges freezer/manual overlap within one owner, preserves all original purchase lots and manual selections, retains zero-quantity records as No, and uses stable entry IDs. Multiple lots are not summed: the first lot by stable ID supplies optional display context; every original lot remains in the archive. A positive legacy source makes a newly migrated entry Yes. Existing new-model decisions and tombstones take precedence.
- Ambiguous legacy groups (for example broccoli/cauliflower or cottage cheese/sour cream) become custom entries retaining the original group name. They require an explicit catalog match before affecting recipes; do not infer a specific ingredient. Unknown legacy IDs are also retained. The `needsCatalogMatch` list supplies the future migration explanation UI.

This slice does **not** activate migration, change current APIs, or enable pantry UI. The next slice must persist migration output and its completion marker atomically. Migration input must already have been validated and loaded from its original verified account or eligible private guest context. A supplied owner string is an internal precondition, not authentication.

## Slice 2: persistence, API compatibility, and sync

Use additive `user_pantry_entries`, `user_pantry_mutations`, and migration/archive storage alongside existing freezer records. Keep purchase history separate from availability. Use text entry IDs (including deterministic migrated IDs), nullable ingredient IDs, normalized custom-name keys, boolean availability, optional metadata, integer revisions, timestamps, and deletion tombstones. Enforce owner-scoped uniqueness for catalog IDs and normalized custom names; indexes must cover owner lookups. Tombstone identities remain reserved, with explicit re-add using their latest revision.

Account ownership comes from the verified server session. Enforce matching ownership through RLS and transaction functions; callers cannot choose their owner. Use the same isolation and revision semantics for the local SQLite fallback. See the current [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) and [database function guidance](https://supabase.com/docs/guides/database/functions). Keep writes behind an atomic mutation function with explicit execute grants; do not expose a table write path that bypasses revision checks.

Implement `/api/pantry` reads and per-entry put/delete mutations. Each mutation carries an idempotency ID and expected revision. The server atomically checks the revision, changes the entry, increments the revision, and records its acknowledgment. Reusing an idempotency ID with a different payload is an error. A stale revision returns a conflict and the current entry/tombstone; the pending edit remains queued. Retrying after a remote deletion requires an explicit user choice, never automatic resurrection. Catalog re-linking must detect identity collisions transactionally rather than discard another entry's metadata.

Persist migration entries, original-source archive, and the owner-specific completion marker together. Read legacy account freezer records and manual preferences in that same transaction. Keep guest migration in its private context; importing into an account is a separate explicit action. Preserve account entries/details on import collisions, preview/report the collisions, and give imports durable idempotency IDs.

Before activating new UI, fence legacy freezer writes and `freezerItems`/`onHandIngredientIds` sync writes for migrated owners. Return an explicit upgrade-required response when they cannot be translated without losing availability, metadata, or revisions. Do not allow an old replacement snapshot to overwrite the pantry. Keep legacy reads and unrelated preference/saved-recipe updates compatible. Update OpenAPI and both generated copies with these API changes.

Queue per-entry mutations under owner-scoped cache keys. Guest and account state must have distinct keys; never copy signed-in data into legacy unscoped guest keys. Preserve pending mutations, conflict details, and the active owner's cache across reloads. Switching accounts must cancel/invalidate in-flight results and hide the previous owner's data. Clear a mutation only after its matching owner/idempotency acknowledgment. Include entries, archived purchases, and pending-data cleanup in export/deletion.

## Slice 3: management UI

Build an accessible Virtual Pantry panel with primary Yes list, No filter, search over catalog and private custom names, optional quick-add shortcuts, explicit Yes/No labels, editing, and deletion. Secondary fields accept blank quantity/location/unit/date. Explain unmapped custom/legacy entries and offer explicit catalog linking. Re-add existing entries by identity without erasing details. Show Saved, Pending sync, retry errors, and conflict resolution. Provide an explicit guest-import preview/action.

## Slice 4: recipe and shopping integration

Make pantry availability the only source for dashboard on-hand toggles and all recipe paths, including authenticated AI requests and saved-recipe displays. Convert each blueprint's free-text staples into explicit requirements and reviewed alternatives, preserving dietary constraints and explicit selections. Keep legacy saved recipes intact and show unknown identities as uncovered until reviewed. Wire static staple estimates into additional grocery totals, including serving scaling; remove flat allowances and inventory-derived savings claims. Available ingredients must not count as measured savings or appear among shopping needs. Update printable/clipboard/cart exports too.

## Slice 5: verification and rollout

Rename current product surfaces and docs, preserving historical release notes. Test account isolation, explicit import collision handling, offline/reload retry, acknowledgment loss, stale concurrent edits/deletes, legacy-write fencing, export/deletion, and keyless operation. Add smoke coverage for quantity-free add → save → reload → recipe/shopping, and keyboard/mobile coverage. Verify account persistence across fresh sessions and a second device in staging before release. All implementation PRs require local typecheck, lint, unit/smoke tests, build, CI, preview, and completed Codex review; the production release also requires regression coverage and the release checklist.

## Application-owned provider boundary

`RecipeProvider.generate` accepts a system instruction, prompt, portable response schema, output-token bound and AbortSignal; it returns text. SDK clients, credentials, model names and native schema syntax stay in adapters. The recipe service owns prompt/context preparation, full local output validation, derived metadata and authoritative repricing. HTTP routes own request authorization and account context. A future speech service can use the same access/quota/error policy with its own audio/proposal contract; it is not forced into the recipe interface.

The existing `@google/genai` 3.0.0 adapter and `gemini-2.5-flash` are retained for compatibility, as required by AGENTS.md, until #731/#752 accept a deliberate replacement. The adapter uses the existing explicit v1beta endpoint and translates the portable schema to Google's native syntax. No second SDK or gateway dependency is needed to establish this boundary. Another provider implements the same small interface; contract tests use a non-Google fake to prove that the service does not need Google SDK objects.

This foundation does not copy the spike's smaller output shape into the application. It retains the real `RecommendedDish` generation fields: macros, market slots, pantry requirements, cooking method and reheating. The selected provider must pass this application contract in #752.

## Output and execution contract

The provider returns exactly three distinct dishes, with the requested servings. All required fields and enum values are checked locally. Numeric values must be finite, nonnegative and at most 1,000,000; ingredient quantities must be positive. Arrays are limited to 64 elements, individual strings to 16,000 characters and the complete response to 256,000 characters. Steps must be present. Known ingredient IDs must be exact catalog IDs. An ingredient outside the catalog needs an explicit `unmapped:` ID and a display name; it stays unpriced rather than becoming a guessed catalog match.

The service imposes a 45-second deadline and passes cancellation to the adapter, with a 6,000-output-token bound. The compatibility adapter makes one attempt, with no SDK retry. A deadline also rejects when a provider ignores cancellation; cancellation is not evidence that billing stopped. #664 must reserve the applicable maximum before dispatch and retain uncertain exposure when its accounting is implemented. There is no automatic cross-provider fallback, retry or refund.

Provider-supplied IDs, saved-state flags and derived metadata are discarded. The app creates fresh `ai-dish-` IDs and derives dietary tags, macro badges and pinned/on-hand state from the request context. It whitelists the output fields used by the application. Model cost estimates, market labels and availability never authorize price calculations: existing `applyPantryToRecipe` recomputes observed/static/unpriced costs, optional requirements, exact identity rules and availability. Non-priced ingredients remain visibly incomplete.

System instructions treat dietary settings as authoritative and notes/store labels as untrusted data. Format and catalog validation do not certify dietary or culinary safety; #731 human review and #752 application acceptance remain necessary. The application never mutates inventory during generation.

## Error and access contract

The shared service exposes only fixed application errors: `PROVIDER_UNAVAILABLE`, `INVALID_RESPONSE` and `TIMEOUT`. Vendor exception bodies, credentials and SDK messages are not returned. The route returns 502 for unusable/provider output, 504 for a generation deadline, and a fixed generic message for unexpected internal failures. Model/vendor branding is absent from generation success/fallback text.

The #749 foundation preserves existing verified-account authorization for app-funded requests and existing deterministic no-key behavior. The transitional `geminiApiKey` request path remains until #751 removes it across UI/API/schema/docs together; retaining it temporarily is not the v1.7 acceptance outcome. The current in-memory limit is also transitional and cannot satisfy #664's shared enforcement criteria.

#751 must remove the key modal/state/request property and any evidenced legacy app-managed persisted keys without uploading values or clearing unrelated pantry data. Stale clients must never execute a submitted key. Request shape, size and enum limits must be enforced before paid dispatch. Guests/local profiles get a clear sign-in action; verified cloud identity remains server-enforced. Preserve owner/context fences across in-flight generation, account switches, retries and saving recipes. Retain deterministic/manual use during configuration errors, outages and quota exhaustion.

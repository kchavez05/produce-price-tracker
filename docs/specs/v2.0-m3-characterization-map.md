| Tab strip | `activeTab`, `data`, `effectiveOnHandIds`, `pinnedIds`, `shoppingPlan`, `trioTotals` |

Cross-module couplings that the provider must expose, not hide:

- **`syncDashboard` is called from the header, stores modal, Meal Plan and about a dozen handlers.** It reads nine values and defaults them from the current render (lines 335-345).
- **Every preference change clears the AI plan** (`setCustomAiDishes(null)`) and runs `pushCloudSync` and `syncDashboard`. Handlers at lines 383-535 follow this pattern; the sequence order matters.
- **Shop reads Plan output.** The Shopping List is built from `activeTrio` (the Plan's three dishes), so Shop cannot render without the Plan's ranking. The provider owns ranking, not the Plan module.
- **The Pantry panel (`VirtualPantry`) is a header toggle**, not a tab, and `handleToggleOnHand` and `handleReviewStockUp` open it from Shop and Radar.
- **`customAiOwner` and `customAiContext` are refs read during render** (line 706) to decide whether the AI plan is stale. They cannot move to a child without changing when the plan is invalidated.

## 4. Persistence and network contract

`localStorage`, restored in one mount effect (lines 229-290), written by handlers:

| Key | Restored | Written by |
|---|---|---|
| `mead_checked_items_v03` | yes | `toggleCheckedItem` |
| `mead_clipped_coupons_v03` | yes | `toggleClippedCoupon` |
| `pantrybot_nutrition_profile_v12` | yes | `persistProfileToLocalStorage` (macro, dietary, vessel) |
| `pantrybot_active_stores` | yes | `handleToggleActiveStore` |
| `pantrybot_user_zip` | yes, and triggers a `syncDashboard` | `handleZipSubmit` |

Pins and servings have **no local persistence**: they live in state and in the cloud preferences only. A page reload resets them for guests. Any change to that is a behavior change.

The mount effect restores in this order and passes the loaded nutrition profile and stores explicitly into `syncDashboard`, because state updates are not yet visible in that closure. A move must keep that order and the explicit passing.

Network calls from the dashboard: `GET /api/dashboard` (`syncDashboard`), `GET/POST/DELETE /api/saved-recipes`, `POST /api/ai-meal-plan` (still sends `geminiApiKey`; v1.7 removes it), `GET/POST /api/cron/weekly-sync`. `usePantry` and `useUserSync` make their own calls and are consumed unchanged.

Ownership guards to preserve exactly:

1. `syncDashboard` and `handleToggleSaveRecipe` capture `pantryOwnerRef.current` before the request and drop the response if it changed (lines 346, 362, 538, 547).
2. `handleGenerateAiPlan` does the same and also records `customAiOwner` and `customAiContext` (lines 558-585).
3. Saved recipes show only when `savedLibrary.owner === pantry.owner`, or when the library is the SSR guest library and the pantry is a guest (lines 194, 223).
4. `pantryAccountId` comes from `userSync.lastSyncedIso` and `initialAccountId` (line 192).

## 5. What the six existing tests pin down

| Test | Behavior covered |
|---|---|
| `dashboard-sync` (4) | meal costs recomputed and the edit retained across an offline pantry deletion until reconnect; pins and servings preserved across a preference acknowledgment; offline guest import retained through a later addition and reconnect replay; a failed guest enqueue retried once |
| `pantry-plan-refresh` (2) | a generated plan stops showing when availability changes, with no new AI request; the plan is retained when only quantity or date changes |

Both mock `usePantry` and `useUserSync` entirely and stub `fetch`. They find controls by button text (`2. 3-Dish Meal Prep`, `Remix 3-Dish Plan`), so any label or tab-name edit breaks them. Related unit coverage for the logic the dashboard calls exists for the shopping-list optimizer, the cart exporter, pantry recipes and `dashboard-permutations`. There is no unit test file named for `meal-prep-matcher` or `pantry/pricing`.

## 6. Coverage gaps that matter for M3

Not exercised by any current test, and each is a way a "verbatim move" could silently break:

1. **Mount restore** of the five keys, including the ZIP-driven refetch with explicitly passed values (line 270-285).
2. **`syncDashboard` ownership drop** when the owner changes in flight (line 362).
3. **Cloud hydration** (`handleCloudHydrated`): ZIP validation, store list, nutrition preferences, pins, saved library owner (lines 160-184).
4. **Checklist and coupon persistence** across reload.
5. **ZIP submit** validation, `pushCloudSync` and error path.
6. **Stores modal** toggling with the "at least one store" rule (line 463).
7. **Alerts modal** preview fetch, manual sync error branches and digest copy.
8. **Save and unsave recipe** including the owner check and failure banner.
9. **AI plan** error and `usedAi` messaging, and the owner and context invalidation (partly covered by `pantry-plan-refresh`).
10. **Print slip** and clipboard output (the cart exporter itself is unit-tested; the wiring is not).
11. **Tab switching and `expandedDishIds`** behavior.

## 8. Move-order risks specific to this file

- **Extract state last.** `syncDashboard`'s nine positional defaults are read from the current render; moving it into a hook changes which values handlers see unless call sites pass every argument as they do now.
- **`onSyncAcknowledged` is an inline closure** (line 188) capturing `storeFilter`, `pinnedIds`, `effectiveOnHandIds` and `targetServings`. Whether `useUserSync` calls the latest or a stale copy decides the "pins and servings preserved" test. Check `useUserSync` before moving it; the existing test is the guard.
- **Mount effect closure.** It runs once with the initial render's values. Moving it into a provider must keep first-render values, not later ones.
- **Render-time ref reads** (line 706) must stay in the component that renders the plan.
- **Print slip uses `window.print()` after a 150 ms timeout** (line 837); jsdom goldens cannot cover it, so it needs the M2 browser suite.

## 9. Suggested M2 smoke journeys that cover the gaps

The M2 plan's first-cut journeys (section 5 there) cover ZIP and store filter, pantry entry and reload, the account modal, the keyless meal plan with shopping list and cart export, static pages and a keyboard pass. They do not cover the persistence, stores modal, alerts or print-slip gaps, so these would be additions:

- Reload keeps checklist, coupons, ZIP, stores and nutrition profile (gaps 1, 4).
- Change ZIP, toggle stores, see the dashboard refresh (gaps 5, 6).
- Switch modules mid-edit and keep pins and servings (M3 Phase B risk).
- Second browser context does not see the first context's pantry (ownership).
- Open the alerts modal and print slip (gaps 7, 10).

Gaps 2, 3 and 8 need jsdom tests with mocked owner changes and cloud hydration, since a keyless browser run cannot simulate them.

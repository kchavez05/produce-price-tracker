## 1. Purpose and Scope

Apply the approved v2.0 design (wireframes, Ledger tokens, M1 primitives) to every screen, on top of the M3 modules and routes, and replace M3's temporary tab strip with the final navigation. M4 is the first milestone that changes what users see; it still changes no sync, auth, ownership, pricing, scoring or zero-key behavior.

In scope (spec section 5): Shop, Pantry and Plan screens; navigation chrome (TabBar, Sidebar, header avatar and menu); onboarding and Settings; account and sign-in; the Data Explorer; legal and docs pages. Also the follow-ups the spec carries to M4 (section 8 of the spec): verify derived device sizes, find out whether Safari exposes fold information, check manifest `orientation`, apply the 3:1 control-border token, map Explorer CSS onto tokens, re-baseline visual snapshots per screen PR, and ratchet down the raw palette classes.

Out of scope:

- Any change to `usePantry`, `useUserSync`, `src/lib/sync`, `src/lib/pantry`, ownership, auth, pricing or scoring (spec section 6: separate reviewed PRs if ever needed).
- New product features. The shopping list is relocated, not expanded; pantry amounts, the stronger shopping list and per-trip store overrides stay out.
- The WCAG AA sweep, the performance budget and release documentation (M5; see decision 15).
- Native apps, Android, desktop-specific layouts, iPhone landscape and iPhone Duo posture handling (deferred by the spec).

## 3. Approach

1. **Shell first, then screens, then secondary pages.** Final navigation and Settings land before the screens that depend on them, because Shop cannot drop its ZIP and store controls until Settings and onboarding exist (decision 1).
2. **One screen per PR (or fewer, larger ones split along the section lines below).** Each PR replaces raw palette classes with tokens and primitives for its screen only, re-baselines its own visual snapshots, clears its own axe allowlist entries and lowers the ratchet (decision 10). It is labelled `run-tier3` so the full matrix, dark mode and snapshots run on the PR.
3. **Behavior parity by tests, not by DOM equality.** M3's golden-HTML guard ends at Phase B. M4 relies on the M2 smoke journeys (locators through the page objects), the six sync and plan jsdom tests, and new component tests for any new presentational logic. Journeys are edited when a control moves (for example ZIP to Settings), and the PR explains each edit.
4. **Design source of truth is the wireframes plus the tokens.** Wireframes show layout and content; spacing, color and type come from M1 tokens. Where a state is undrawn, decision 5 says what happens.
5. **Dark mode and light mode ship together** in every screen PR (decision 9).

## 5. Behavior That Must Not Change

- Everything in M3 section 5: ownership and sync (a cloud error never acknowledges a pending change; queued changes stay bound to their account), zero-key behavior, persistence keys and hydration safety, pricing and unit-price guards, the "Buy 2: Prep 1, Freeze 1" math, authenticated server-funded AI.
- **Guest privacy.** Onboarding and Settings write guest preferences to the device only, under the existing keys and formats (decision 3); signing in syncs them through the existing path with no changes to sync code.
- **Defaults.** Skipping onboarding keeps today's defaults (ZIP 80542, all stores). A returning user with stored ZIP or stores never sees onboarding.
- **Nothing required in Pantry.** No screen blocks or nags for pantry data (flows document, 2a).
- **Print and forced-colors.** The printable shopping slip and the forced-colors fallback keep working.
- **Hydration.** Theme and preference restore stay post-mount; no flash, no hydration warnings.

## 6. Risks

- **Many visual changes at once.** Mitigation: one screen per PR, per-PR baselines in both themes, `run-tier3` label, and a Preview check on a real phone for each Shop, Pantry and Plan PR (decision 13).
- **Plan drift.** M1 to M3 are not implemented; names (`TabBar`, `Sidebar`, `/design`, page objects) may change. Mitigation: re-survey at the start of M4 and update this document in its tracking PR.
- **Undrawn states invented ad hoc.** Mitigation: decision 5.
- **Settings and onboarding move controls users know.** Shop loses its ZIP and store row. Mitigation: the read-only line on Shop links straight to Settings; a changelog note in release docs; no per-trip override (already decided).
- **PWA behavior unverifiable in CI.** Orientation, safe areas, status bar style and home-screen icons only show on real devices. Mitigation: a manual device checklist (decision 13) and keeping these changes small and separate (decision 12).
- **Long leaderboard.** Value Board measured about 23,000 px tall. Restyling alone will not fix it. Mitigation: sectioning and paging are part of the Shop PR (decision 15), not deferred.
- **Explorer and Swagger are large and third-party-shaped.** Rewriting them would dwarf the rest of M4. Mitigation: restyle at the token and shell level only (decisions 6 and 7).
- **Review fatigue.** Mitigation: every PR says which snapshots changed and why, and lists the palette-class count before and after.
- **Baseline growth.** Each re-baseline adds PNGs, now in two themes. Mitigation: the 25 MB review point in M2 decision 6; dark snapshots limited to key states (decision 9).

## 8. Test Strategy (Builds on M1 and M2)

- **Per screen PR:** Tier 1 unit and component tests for new logic and primitives usage; Tier 2 browser smoke with axe at 390 and 820; `run-tier3` label for the full matrix (390, 402, 440, 820, 1194, 626), Chromium cross-check, dark mode and visual snapshots.
- **Snapshots:** the PR regenerates its own screens' baselines through the CI-only update workflow (never from a laptop) and says so. A diff on a screen the PR did not touch is a failure to explain.
- **Axe allowlist:** entries for the screen being redesigned must be removed in the same PR; new serious or critical violations fail (M2 decision 7).
- **Ratchet guard:** raw palette class counts for migrated files go to zero, and the stored baseline is lowered in the same PR.
- **Width, not model:** assertions are by width class (TabBar versus icon rail versus Sidebar, no horizontal scroll), per the device specs.
- **Manual:** the real-device checklist in decision 13.

- The Data Explorer, `/privacy`, `/terms`, `/docs` and `/api-docs` use tokens and work in dark mode and at 390 wide.
- No raw palette class remains in migrated files; the repository-wide count is zero (decision 10); the axe allowlist for these screens is empty.
- Visual baselines (light and dark) exist for every redesigned screen and were regenerated only by CI.
- The manifest follow-ups are resolved or recorded as unresolved with evidence; the real-device checklist has been run on an iPhone and an iPad by the owner.
- Sync, ownership, pricing, scoring and zero-key behavior unchanged; same `localStorage` keys; no new runtime dependency; no `any`; no new `eslint-disable`.

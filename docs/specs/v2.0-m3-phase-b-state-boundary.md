## 1. Where Phase A Left Things

Phase A (extraction in place, PRs #782 to #804, interleaved with CI and test-reliability fixes) is complete. `MealPrepDashboard.tsx` went from 3,557 lines to 1,024 and has no `eslint-disable`. What remains in it:

- **About 670 lines of logic:** 25 `useState` calls, five hooks extracted in M3 (`usePreferencesState`, `useLocationState`, `useAccountAndPantry`, `useDashboardPayload`, `useStorageRestore`) on top of the existing `useUserSync` and `usePantry`, about 20 handlers and the derived-data chain.
- **284 lines of JSX:** a header, four drawers and a `<main>` that renders one module section at a time.
- **Module components under `src/modules/`:** `shell` (header, nav, ZIP, stores, alerts), `shop` (Board, Trip, Radar, badges), `plan` (header, dishes, blueprints). They are stateless and receive everything as props. The Pantry drawer is still `VirtualPantry` in `src/components`.

The spec's stop point for Phase A is a "thin composition". That is not reachable without deciding where the remaining state and handlers live, which is exactly the question Phase B has to answer anyway.

## 2. The Constraint That Decides the Boundary

Acceptance criterion 9 says the routes work and **state survives module switches**. Today that is free: the tab sections unmount when inactive, but every piece of state lives in the one parent component, so nothing is lost. After Phase B each route renders its module separately, so any state held inside a module component would reset on navigation.

So the boundary is not "which module owns this handler". It is **which state must survive navigation**. Today's behavior is that all of it does, including pure view state (the sort mode, an expanded dish, "show all blueprints"). Anything we move into a component to make a module "self-contained" is a behavior change.

## 4. Cross-Module Couplings That a Naive Split Would Break

1. **The shopping list depends on the Plan's AI choice.** `customAiDishes` (Plan) feeds `activeTrio`, which feeds `shoppingPlan` and the Trip view (Shop) and the nav count. The derived chain must live above both modules.
2. **The store bar sets Shop state.** `handleStoreChange` sets `storeFilter` and `tripMode`, and clears `customAiDishes` (Plan).
3. **Shop actions invalidate Plan state and refetch.** `handleTogglePin` clears `customAiDishes` and calls `syncDashboard`; the preference handlers (Plan UI) also push to the cloud and persist.
4. **Shop actions open Shell and Pantry UI.** `handleReviewStockUp` and an unmatched `handleToggleOnHand` open the pantry drawer and set the toast.
5. **Plan opens a Shell modal.** `showAiSignIn` sets `accountIntent` and opens the account modal.
6. **Tab switches become navigation.** `setActiveTab('MEAL_PLAN')` ("View 3 Dishes") and `setActiveTab('SHOPPING_LIST')` (Plan header) become links.
7. **The AI request fence reads every preference.** `mealContextSignature` and the owner ref are built from the whole preference set plus the pantry owner.
8. **Pins, servings and the store filter are not persisted locally** (only the profile, active stores, ZIP and the two checklists are; signed-in users also get preferences from the cloud on load). They survive navigation only while the provider stays mounted, which is why it has to sit in the layout.

## 5. Proposed Boundary

**Provider (route-group layout, one client component), split into several contexts so a change re-renders only its readers:**

- **Preferences:** the seven preference states and their actions (macro goal, dietary, vessel, active stores, pin, servings, store change, clear filters).
- **Location:** the ZIP state and `handleZipSubmit`.
- **Payload and derived data:** `useDashboardPayload`, plus one hook that owns the derived chain (`data`, `activeTrio`, `trioTotals`, `shoppingPlan`, `resolvedShoppingItems`, `digitalCouponItems`, `filteredCommodities`). It reads `customAiDishes`, so it sits above Plan.
- **Account and pantry:** `useAccountAndPantry` as it is today.
- **Plan UI memory, Shop UI memory, Shell UI:** the view-state groups from section 3, held in the provider and exposed through narrow hooks (`usePlanUi`, `useShopUi`, `useShellUi`).

**Modules** stay stateless views over those hooks, as they are today. Module-specific handlers (AI plan, checklist toggles, copy and print, alerts and weekly sync, save recipe, promote) become hooks beside their module, called from the provider so the state they touch survives navigation.

This keeps today's behavior exactly, at the cost of a larger provider than a purist "module-local state" design. Narrowing view state to component-local later is a separate, visible behavior change and belongs to the M4 redesign if wanted.

### Decisions (settled 2026-11-18, owner)

1. **Preserve all state across navigation, or reset pure view state?** **Decided: preserve all of it.** (Recommendation adopted.) Preserving is the spec's acceptance criterion and changes nothing. Resetting view state (sort mode, category filter, expanded dish, show-all blueprints, copied flags, print-slip modal) would simplify the provider but is a small user-visible change in eight places, so it needs your OK.
2. **What happens to the header Pantry drawer?** **Decided: make the header Pantry button a link to `/pantry` for now.** The drawer overlay goes away with the route; the toast and the "review your Pantry" actions navigate to `/pantry` (the toast lives in the Shell context, so it survives the navigation). Anything fancier is M4. Today it overlays any tab. The spec adds `/pantry` as a route. Options: keep the drawer as is and add the page later; make the drawer a link to `/pantry`; or render both from the same component. The toast and "review your Pantry" actions need to land somewhere.
3. **Do the preference actions as a last Phase A PR (A.5d) or fold them into the provider PR?** **Decided: A.5d now, as its own PR.** I recommend A.5d. This revises my earlier "no generic actions hook" advice, which was too broad. This group is always provider-level whichever option is chosen, it has the same four-step pattern in every handler (set state, persist, push to the cloud, `syncDashboard`), and it is about 200 lines.

## 7. Risks Specific to Phase B

- **Re-render breadth.** One large context would re-render every module on any change. Mitigation: the split contexts above, and golden or render-count checks where a context is added.
- **Hydration.** The provider is a client component fed server-loaded initial data from the layout. The first render must stay identical to the server render (the same constraint `useStorageRestore` already respects).
- **Navigation while a request is in flight.** `syncDashboard` and the AI request fence use owner refs, not component lifetime, so they survive a module switch only if they live in the provider. They must not move into route components.
- **Locator churn.** Link-based navigation changes how the Playwright page objects reach each module. Keep it inside the page objects and keep the Tier 2 and Tier 3 journeys unchanged.
- **Scope creep from the pantry decision.** A `/pantry` page is new UI surface; decision 2 should keep it as small as the spec allows.

## As Built (2026-11-19)

The breakdown in section 6 was followed. Where the build differs from the proposal:

- **B.1 took five PRs** (#811 to #815): the derived chain, Shop UI, Plan UI with the AI actions, Shell UI, then `AppProvider` and the seven contexts (Preferences, Location, Dashboard, Account, Plan, Shop, Shell). The narrow hook names are `use<Name>Context`.
- **B.2 took four PRs** (#816 to #819). The Pantry and the account dialog got module adapters (`PantryDrawer`, `AccountDialog`) that read the contexts; `VirtualPantry` and `AccountModal` moved into `src/modules` and stay props-driven so their own tests are unchanged.
- **B.3 was split into five steps**: a visual-job prerequisite (#820), the module and Shop-view model (#821), the Pantry as a module (#822), the routes (#823) and the browser journeys (#824).
- **The router is behind a seam.** Only `src/modules/shell/app-router.tsx` imports `next/navigation`; the hooks read a small `AppRouter`, and Tier 1 tests use an in-memory router (this replaced the "pending navigation target" idea in the risks below).
- **The module is derived from the URL.** `navigateTo` (Shell context) is the single navigation path and pushes a path only when the module changes; Shop views stay state.
- **The Pantry remembers where it was opened from** (`pantryReturn`), and the header Pantry control is a link that does not toggle.
- **Pantry local UI state is not preserved** across leaving the Pantry (owner decision, option a), the one exception to decision 1.
- **`/` reads a cookie** (`pantrybot_last_module`, module name only) rather than local storage, per decision 10 of the plan.

# v1.6.0 — Virtual Pantry

Virtual Pantry replaces quantity-based freezer availability with explicit Yes/No ingredients across pantry, fridge, and freezer. Recipes retain the amount needed while showing what is already available and the estimated additional grocery cost.

## Inventory and persistence

- Add a catalog ingredient by name without entering quantity, price, or location. Optional shortcuts never preselect inventory; private custom entries remain available.
- Edit availability, storage location, quantity, unit, and use-by date. Quantity zero, blank quantities, and past dates do not change Yes/No. No preserves details; deletion retains conflict-safe tombstones.
- Guests save privately on the current device. Signed-in inventory uses session-derived ownership, PostgreSQL RLS, per-entry revisions, idempotent acknowledgments, and durable account-bound offline queues.
- Guest import requires review and confirmation; existing account entries win duplicate collisions. Failed writes stay pending, and concurrent edits require explicit resolution.
- Legacy freezer lots and manual on-hand selections migrate once with stable IDs and retained source records. Unsupported older quantity writes are fenced rather than overwriting pantry data. Export/deletion covers pantry records and owned recovery data.

## Cooking catalog and recipe coverage

- The approved catalog contains 72 cooking identities, including Dried lentils, Canned lentils, and Onions. Broad lentil search presents two primary forms; red lentils remains an optional, directly searchable variety.
- USDA source snapshots, fingerprints, decision approvals, diffs, quarantine exceptions, and deterministic artifacts support repeatable ingestion. The initial 74 unresolved Foundation rows remain held under the approved release-scoped exception through April 30, 2027.
- Every pantry identity has a market-link applicability audit: 15 current links and 57 explicit no-current-counterpart dispositions. Catalog/matching-rule changes require re-audit. No name/family similarity creates an automatic match or price.
- Reviewed red dried lentils can cover a general dried-lentil requirement. Explicit No for the required identity wins; general-to-specific and dry/canned inference are disallowed.
- Fresh Onions cover the reviewed cooking-onion recipe requirement, with a separate link from its market pricing ID. Onion powder remains a separate staple. The mixed recipe tests neither, fresh-only, powder-only, and both availability states, including costs and shopping needs.
- Available recipe cards show “Make sure you have” with the recipe quantity and $0.00 additional cost. Distinct required coverage and shopping needs refresh together. Staples retain labeled fixed estimates; missing identities/prices/units remain explicit uncertainty.
- Buying, planning, saving, cooking, source refreshes, and catalog publication never deduct or modify inventory. Pantry uses a door icon; freezer-specific snowflakes remain.

## API and compatibility

`/api/pantry` exposes private/no-store snapshots, explicit migration, and revision-checked mutations. Its GET response includes the application catalog version and installed accepted IDs; clients wait for database acceptance before queueing new identities. Compatible cache/queue readers preserve unfamiliar IDs and owner binding. PostgreSQL and SQLite retain accepted IDs across presentation rollback. OpenAPI is versioned 1.6.0 and both generated schema copies are updated.

## Validation and release gates

Local validation covers catalog projection/audit checks, typecheck, lint, 277 unit tests, 19 smoke tests, 37 regression tests, and a production build. Earlier local browser and HTTP verification exercised quantity-free add/save/reload, new IDs, idempotent retry, recipe costs/coverage, compact search, optional varieties, and accessibility controls. PostgreSQL/PGlite and SQLite suites cover isolation, persistence, legacy fences, conflicts, queues, exports/deletion, and rollback. The release PR must additionally pass CI, Vercel Preview, and completed Codex review.

Hosted rollout is a separate release gate. Before enabling production:

1. The maintainer explicitly authorized direct production rollout and testing on October 30, 2026, replacing the isolated-staging gate for this release. Use dedicated test accounts and private guest sessions for verification; do not modify customer inventory.
2. Apply `20261029171953_virtual_pantry_persistence.sql`, `20261029211728_pantry_staple_catalog.sql`, and `20261030173404_reviewed_cooking_catalog.sql` in order, then verify all 72 accepted IDs and access boundaries.
3. Deploy compatibility-capable code before clients can save new IDs. Enable `PANTRYBOT_PANTRY_ENABLED=true` only after the migrations and database checks succeed; retain the safe disabled default elsewhere.
4. Verify the production version, pantry add/save/reload, recipe/shopping behavior, and runtime errors before publishing the GitHub Release. Record environment and deployment evidence in the release record.

## Rollback and deferred scope

Use the compatibility-capable code with `NEXT_PUBLIC_PANTRYBOT_CATALOG_VERSION=baseline-1.5.2` for catalog presentation rollback. Retain accepted database IDs, inventory, source/approval history, and pending queues. Do not roll back to incompatible readers or restore inventory from a database backup as a UI rollback.

Speech entry is planned for v1.6.1. Barcode lookup and dynamic staple pricing remain v1.6.2. Additional ingredient batches require their own curation and product review; this release does not activate the USDA candidate pool or schedule recurring ingestion.

## 3. Qualify production ingress before activation

Existing qualified enforcement is Preview-only. Production observation/default-off behavior is not shared enforcement. Inspect current published configuration and any draft; stage the intended production route + POST + production-environment rule without publishing unrelated changes. The operator reviews/publishes the staged rule through the established firewall workflow.

Require 30 attempts/IP/60-second fixed window **per edge region**, including failures, with excess 429. Record exact rule/environment scope and ordinary-browser threshold/reset, concurrency/shared-counter and forwarded-IP/route-variant evidence as applicable to the actual production ingress. CLI/protection-bypass traffic is not WAF acceptance. Independent regions can exceed 30 combined; do not claim a global cap. Keep raw barcode bodies, frames, household inventory and owner identifiers out of retained diagnostics; verify actual logging/drain/retention configuration for the production environment.

The supplemental process limiter reserves independent capacity for its 18 trusted route scopes within a 5,000-bucket process budget (277 identities per scope). Saturation can reject new identities in that scope, never another scope; existing counters are not evicted. This local capacity guard is separate from the per-IP request allowance and cannot replace shared WAF enforcement. Record the actual deployed Node runtime/version and recheck it supports the read-only SQLite path used in the artifact qualification.

Only set `PANTRYBOT_BARCODE_SHARED_LIMIT_VERIFIED=true` after supported production-scoped evidence. It is an attestation, not the limiter. Preserve the platform boundary; do not add an unqualified proxy. Document the operator/rule receipt before enabling public lookup/camera.

If activation fails, disable lookup/camera and redeploy as needed; retain manual pantry use, owner inventory and saved recipes. Restore a known reviewed source/artifact pair when appropriate, never replace an index in place. Record the previous production deployment before rollout. After required production acceptance passes, update candidate notes/changelog with the actual verified date, source/deployment/rule/test/cleanup receipts and explicit verification limits via the required PR workflow. Synchronize main/develop through approved repository procedures without overwriting another worktree or bypassing branch protections. Publish/tag v1.6.2 on the verified main commit, then close only accepted feature issues, release parent #645 and milestone 8. A pending deployment or accepted pre-release exception alone does not authorize publication.

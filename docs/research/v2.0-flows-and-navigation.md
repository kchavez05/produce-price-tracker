# v2.0 Flows and Navigation — Draft

Status: Draft; navigation decisions recorded 2026-11-11 (section 2a). Input to [v2.0 M0](../specs/v2.0-ui-redesign.md). Based on the [current UI audit](v2.0-ui-audit.md). Module names are working proposals; tab order is decided.

## 1. Modules

| Module | Job | Owns | Reads from |
|---|---|---|---|
| **Shop** | Find the best prices and plan the trip | Value board, cycle/club radar, store split, shopping list, cart export, coupons | Pantry (what is already on hand), Plan (ingredients needed) |
| **Pantry** | Know what is at home | Virtual Pantry entries, quick add, barcode/camera (v1.6.2), freezer/arbitrage items | Shop (deal prompts for stock-up) |
| **Plan** | Decide what to cook this week | 3-dish recommendations, servings, saved recipes, AI chef, dietary/macro/vessel preferences | Shop (prices), Pantry (on-hand) |

Cross-cutting, not a module: location (ZIP), selected stores, account/sign-in, and preferences. These live in account configuration and Settings, reachable from every module via the header avatar/menu.

Current tab mapping: Value Board and Radar become Shop sections; Shopping List becomes Shop's "Trip" view; 3-Dish Meal Prep becomes Plan; Virtual Pantry (today a header-toggled panel) becomes Pantry.

## 2. Navigation model

- **iPhone (compact width):** bottom tab bar with Shop, Pantry, Plan; Account/Settings via a header avatar and/or hamburger menu. Large title per screen. ZIP and stores are set in account configuration, not on the Shop screen (see 2a).
- **iPad (regular width):** sidebar with the same destinations; Shop and Plan use a list/detail split (e.g., item or dish detail beside the list).
- **Web/PWA:** the same structure responsive by size class; desktop gets the iPad layout. Each module is a route (`/shop`, `/pantry`, `/plan`) so deep links work and `/` redirects to the last-used module (default Shop). Route names are proposals.
- **Native (v2.x):** the same three destinations map to React Navigation tabs; keep route names and screen names aligned.
- Tab order: Shop, Pantry, Plan (decided; see 2a).

## 2a. Decisions (owner, 2026-11-11)

1. **Tab order: Shop, Pantry, Plan.** The primary question is "What should I get at the grocery store?" because the product's core value is finding the best deal at any time. "What do I already have?" informs it, and "What should I make with it?" comes last.
2. **Each module is self-contained.** Distinct user groups may use mainly one module, so Shop, Pantry and Plan each work fully alone and are improved when used together. Cross-module features (pantry-aware recommendations, "have at home" hints) are progressive enhancements, never prerequisites.
3. **Pantry must not be intrusive.** Most users won't know or track what they have, so no flow may require or nag for pantry data; pantry-aware features degrade gracefully to the same result without it.
4. **Account is a header avatar and/or hamburger-menu entry, not a tab.**
5. **Location and stores live in account configuration**, set once during onboarding, and are kept off the main Shop screen. Shopping habits are mostly static, so they are edited from Settings, not on every visit.

Consequences to design for:
- **Guests have no account.** The zero-key, guest-first behavior still needs a lightweight first-run setup (ZIP and stores) stored on the device, with the existing default (ZIP 80542, all stores) if skipped, and a path to sync it after sign-in.
- **Onboarding** becomes a real flow: ZIP, stores, and optionally dietary and macro preferences, each skippable.
- **Shop's top area** is freed for deals; the current store filter row and ZIP selector move out of it. Shop still needs an in-context way to see which stores are active (read-only label) and to jump to Settings.
- **No per-trip store override on Shop (decided).** Store selection is edited only in Settings.
- **Shopping list enhancements are a separate scope of work.** v2.0 relocates the existing shopping list (Shop's Trip view) but does not expand it; a stronger shopping list is tracked as its own future feature.

## 3. Key flows

### Flow A — Weekly planning loop (primary)
1. **Pantry:** review what is on hand; add or confirm items (manual now; barcode in v1.6.2; speech later).
2. **Plan:** set servings and preferences; see three recommended dishes using on-hand items and current prices; save or swap dishes.
3. **Shop:** see the combined list (ingredients not on hand), best single store or two-store split, coupons; export to a cart or print.
4. **After shopping:** confirm purchases into Pantry (explicit confirmation; no automatic deductions, per the v1.6.0 spec).

### Flow B — In-aisle quick check
Shop, search or filter by category, view unit price vs 6-week low and club price. Optional: add to list or Pantry.

### Flow C — Deal-driven stock-up
Shop alert (cycle low or splurge deal), then "Buy 2, freeze 1" creates a Pantry/freezer entry and shows the trade-off.

### Flow D — First run and guest mode
Guest can use all three modules with private device-local ownership; sign-in is prompted for cloud sync and (v1.7) AI features. Zero-key deterministic behavior must hold in every module.

### Flow E — Account and settings
Sign in/out, sync status and conflicts, ZIP and stores, preferences, privacy, data explorer link, API docs link.

## 4. Per-module screen inventory (for wireframes)

**Shop:** Overview (alerts + top deals) · Leaderboard (filters, sort, category) · Item detail (price history, club benchmarks, actions) · Trip (store split, list, coupons, export/print) · Radar (stock-up vs peak, club matrix, USDA movers).

**Pantry:** List with search and availability · Add/quick add · Item detail · Import/conflict resolution states · Empty and guest-import states.

**Plan:** This week's dishes · Dish detail (ingredients, cost, macros) · Preferences (dietary, macros, vessel, servings) · Saved recipes · AI chef (signed-in only after v1.7; deterministic fallback otherwise).

**Shared:** Context sheet (ZIP, stores) · Account and sync sheet · Settings · Legal and docs.

## 5. Data and state boundaries (for M3)

- Server entry currently builds one dashboard payload (`buildDashboardPayload`). Proposed: each module route loads only what it needs; shared context (ZIP, stores, preferences) via a small provider; Pantry and Plan reading Shop data through existing `src/lib` functions, not new logic.
- Sync and ownership code (`usePantry`, `useUserSync`, `src/lib/pantry`, `src/lib/sync`) must be consumed unchanged.
- Cross-module links (e.g., "Have at home" on a Shop card) use IDs and read-only pantry state.

## 6. Open design questions

1. Does Shop's "Radar" deserve its own destination or stay a Shop section?
2. How much of Plan's preference set belongs in onboarding vs Settings?
3. Guest first-run setup: how much to ask, and when to prompt sign-in for sync.
4. List/detail behavior for iPad mini and the iPhone Duo's inner display (deferred unless cheap).
5. Whether the Data Explorer (`/data`) is promoted into the app shell or stays a linked tool.

Resolved: tab order, account placement, where location/stores live, and no per-trip store override (section 2a).

## 7. Post-MVP Ideas

- **Pantry amounts.** Keep the first choice a plain Yes/No. After choosing Yes, optionally drill down to "Have Lots" or "Have a Little" with +/- buttons (the most discoverable on iPhone), long press, or multi-press. The amount never blocks the Yes, and Shop and Plan treat Yes with no amount exactly as today. Needs its own spec, including how amounts would affect Plan's cost estimates.

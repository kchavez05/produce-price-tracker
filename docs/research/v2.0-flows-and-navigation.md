# v2.0 Flows and Navigation — Draft

Status: Draft for owner review, input to [v2.0 M0](../specs/v2.0-ui-redesign.md). Based on the [current UI audit](v2.0-ui-audit.md). Module names and tab order are working proposals.

## 1. Modules

| Module | Job | Owns | Reads from |
|---|---|---|---|
| **Shop** | Find the best prices and plan the trip | Value board, cycle/club radar, store split, shopping list, cart export, coupons | Pantry (what is already on hand), Plan (ingredients needed) |
| **Pantry** | Know what is at home | Virtual Pantry entries, quick add, barcode/camera (v1.6.2), freezer/arbitrage items | Shop (deal prompts for stock-up) |
| **Plan** | Decide what to cook this week | 3-dish recommendations, servings, saved recipes, AI chef, dietary/macro/vessel preferences | Shop (prices), Pantry (on-hand) |

Cross-cutting, not a module: location (ZIP), selected stores, account/sign-in, and preferences. These live in a context bar and a Settings/Account surface reachable from every module.

Current tab mapping: Value Board and Radar become Shop sections; Shopping List becomes Shop's "Trip" view; 3-Dish Meal Prep becomes Plan; Virtual Pantry (today a header-toggled panel) becomes Pantry.

## 2. Navigation model

- **iPhone (compact width):** bottom tab bar with Shop, Pantry, Plan (+ Account/Settings as a fourth tab or header avatar). Large title per screen; context bar (ZIP and stores) collapses into a single tappable chip at the top of Shop.
- **iPad (regular width):** sidebar with the same destinations; Shop and Plan use a list/detail split (e.g., item or dish detail beside the list).
- **Web/PWA:** the same structure responsive by size class; desktop gets the iPad layout. Each module is a route (`/shop`, `/pantry`, `/plan`) so deep links work and `/` redirects to the last-used module (default Shop). Route names are proposals.
- **Native (v2.x):** the same three destinations map to React Navigation tabs; keep route names and screen names aligned.
- Tab order proposal: Shop, Pantry, Plan, matching the weekly loop below. Alternative to evaluate in mockups: Plan first.

## 3. Key flows

### Flow A — Weekly planning loop (primary)
1. **Pantry:** review what is on hand; add or confirm items (manual now; barcode in v1.6.2; speech later).
2. **Plan:** set servings and preferences; see three recommended dishes using on-hand items and current prices; save or swap dishes.
3. **Shop:** see the combined list (ingredients not on hand), best single store or two-store split, coupons; export to a cart or print.
4. **After shopping:** confirm purchases into Pantry (explicit confirmation; no automatic deductions, per the v1.6.0 spec).

### Flow B — In-aisle quick check
Shop, search or filter by category, view unit price vs 6-week low and club price. Optional: add to list or Pantry.

### Flow C — Deal-driven stock-up
Shop alert (cycle low or splurge deal), then "Buy 2, freeze 1" creates a Pantry/freezer entry and shows the trade-off.

### Flow D — First run and guest mode
Guest can use all three modules with private device-local ownership; sign-in is prompted for cloud sync and (v1.7) AI features. Zero-key deterministic behavior must hold in every module.

### Flow E — Account and settings
Sign in/out, sync status and conflicts, ZIP and stores, preferences, privacy, data explorer link, API docs link.

## 4. Per-module screen inventory (for wireframes)

**Shop:** Overview (alerts + top deals) · Leaderboard (filters, sort, category) · Item detail (price history, club benchmarks, actions) · Trip (store split, list, coupons, export/print) · Radar (stock-up vs peak, club matrix, USDA movers).

**Pantry:** List with search and availability · Add/quick add · Item detail · Import/conflict resolution states · Empty and guest-import states.

**Plan:** This week's dishes · Dish detail (ingredients, cost, macros) · Preferences (dietary, macros, vessel, servings) · Saved recipes · AI chef (signed-in only after v1.7; deterministic fallback otherwise).

**Shared:** Context sheet (ZIP, stores) · Account and sync sheet · Settings · Legal and docs.

## 5. Data and state boundaries (for M3)

- Server entry currently builds one dashboard payload (`buildDashboardPayload`). Proposed: each module route loads only what it needs; shared context (ZIP, stores, preferences) via a small provider; Pantry and Plan reading Shop data through existing `src/lib` functions, not new logic.
- Sync and ownership code (`usePantry`, `useUserSync`, `src/lib/pantry`, `src/lib/sync`) must be consumed unchanged.
- Cross-module links (e.g., "Have at home" on a Shop card) use IDs and read-only pantry state.

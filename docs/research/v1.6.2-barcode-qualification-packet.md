# v1.6.2 barcode qualification packet

Status: proposal for maintainer review, November 9, 2026. No lookup endpoint, camera, shared mapping or rollout is enabled by this packet. The [approved specification](../specs/v1.6.2-barcode-and-staple-pricing.md#9-decisions-required-before-implementation) makes coverage and technical decisions implementation gates. This packet supplies the barcode portion; the independent pricing permission gates remain unresolved.

## Recommended decisions

| Decision | Recommendation |
| --- | --- |
| BQ-01: identifiers and revisions | UPC-A and EAN-13 capture; typed 12/13-digit consumer codes and validated zero-filled 14-digit representations. US snapshot records only. Latest publication date selects a revision; ties, invalid dates and discontinued latest records stay explicit. Defer eight-digit codes/UPC-E, packaging-level GTIN-14, restricted circulation, coupons and other barcode types. |
| BQ-02: lookup storage and operations | Build a versioned, read-only server SQLite index from the retained USDA files. Include all eligible US latest heads plus outcome markers. Keep full source/history outside Git and the app. No additional provider key, paid lookup service or live FDC fallback. Require artifact delivery, tracing, complete function-size and Preview checks before activation. |
| BQ-03: exact suggestion coverage | Review the 16 exact product revisions for 11 accepted generic identities in the mapping packet. All other products require manual catalog selection or custom entry. The 29 held examples receive no automatic suggestion. Every addition requires confirmation. |
| BQ-04: access, confirmation and camera | Equal non-AI lookup for guests and accounts, with private manual entry preserved. Use the existing owner-bound save queue. Lazy-load the proposed ZXing reader on deliberate capture; retain typed fallback. Require deployed abuse controls and real iPhone Safari / Android Chrome verification before enabling the corresponding controls. |

These recommendations need an explicit maintainer decision; this document and a documentation PR merge do not record approval. The [review envelope](../../catalog/proposals/2026-11-09-barcode-qualification/review-envelope.json) fingerprints the exact proposal and evidence. Later amendments need a new reviewed envelope.

## BQ-01: identifier and revision contract

Preserve original input and original source barcode strings separately. Manual input is a string of at most 64 ASCII characters in a JSON body capped at 256 bytes. Allow outer ASCII spaces only; reject internal separators, URLs, Unicode digits, numeric JSON, control characters and arbitrary text. Validate supported length and GS1 modulo-10 check digit before creating a lookup key. Never repair an eleven-digit source code or recover dropped leading zeros by guessing.

Only validated 12/13-digit codes receive GS1 zero-fill to a separate 14-character comparison key. An accepted typed 14-digit string must begin with zero and pass the same consumer-prefix restrictions. Nonzero packaging indicators never collapse to the underlying consumer item. GS1 documents zero-fill equivalence while preserving meaningful original zeros. [GS1 identifier representation](https://ref.gs1.org/standards/digital-link/uri-syntax/1.7.0/), [check digit](https://www.gs1.org.sa/services/check-digit-calculator)

Conservatively exclude the EAN-13-view prefixes `02`, `04`, `05`, `20–29`, `98`, `99`, `977–979`, and `00000`. These are EAN-13 namespace prefixes: UPC-A number-system digits 2/4/5 become 02/04/05. A UPC-A string beginning 02/04/05 instead becomes 002/004/005 and is not rejected by those restrictions. This holds restricted/reserved/nonfood ranges, including zero-filled eight-digit collisions; it is an application support boundary, not a complete GTIN issuance validator. Defer EAN-8 and UPC-E until their format distinction and expansion receive separate fixtures and device verification. QR/Digital Link URLs, DataBar, Code 128 and ITF are outside initial capture. [GS1 prefix specification/change notice](https://ref.gs1.org/standards/genspecs/gscn/2025/GSCN-25-302-Prefix-984-989.pdf)

For each comparison key, retain US records with source market exactly `United States` or `US` after whitespace/case normalization. Use the latest `food.publication_date`, as USDA documents for duplicate product codes. Validate all applicable dates against the snapshot cutoff. Missing, malformed or future dates quarantine that group. Select the newest record before checking discontinued status; an older active record must not be resurrected. More than one newest US record returns ambiguity, never an FDC-ID tie-break winner. Modified/available dates are retained context, not competing sort keys. Never infer US market from barcode prefix. [USDA field definitions](https://fdc.nal.usda.gov/docs/Download_Field_Descriptions_Oct2020.pdf)

An immutable snapshot supplies last-known product information. Its retrieval/build time does not make an old publication current, prove present shelf availability, or certify dietary safety. Display source dates for review. A monthly operator refresh builds a new artifact and diff; it does not auto-publish revised mappings or rewrite pantry entries.

## BQ-02: index delivery and bounded lookup

The size probe supports testing a server-only read-only SQLite file with an indexed key, separate from existing personal databases. Keep the raw CSVs, full audit database and generated index out of Git, `public/`, browser imports and private inventory. Build a finalized index/schema manifest with a digest, record count, source hashes and rules version. Deliver it to the build as an operator-controlled artifact, verify its digest, and trace it only into the lookup route. Never regenerate the index, download the raw dump, or write to the deployed filesystem on a user request. Failed integrity/version checks return service unavailable.

Vercel's standard Node function limit is 250 MB uncompressed, including dependencies. A 110.25 MiB data probe is an input to that budget, not proof that the complete deployed function fits. Use route-specific Next.js file tracing and verify the actual deployment size, Node SQLite support, cold/warm latency, concurrency and read-only behavior. If the complete route does not fit, return an amended storage proposal; do not enable large-function beta, provision a paid service or silently shrink product coverage. [Vercel limits](https://vercel.com/docs/functions/limitations#bundle-size-limits), [Next.js tracing](https://nextjs.org/docs/15/app/api-reference/config/next-config-js/output)

Proposed `POST /api/pantry/barcode-lookup` accepts only barcode text and capture format, never an owner ID, source URL, arbitrary SQL, price or mapping rule. Return an allowlisted product projection with source/snapshot/dates, original code, comparison key, raw package label, revision token and a separately labeled mapping candidate. Do not infer an inventory amount from serving size or package label. Product and ingredient identity remain separate objects.

Outcomes are distinct: invalid, unsupported, not found, ambiguous product, found with/without a suggestion, discontinued, source-date hold, disabled, service unavailable, throttled and internal failure. Offline is a client transport state, not a confirmed missing product. For latest ties above five candidates, return ambiguity with manual correction, not an arbitrary truncated winner. Cap successful bodies at 16 KiB; oversized/unusable metadata falls back to a recoverable service result. Target a two-second lookup deadline; no server retry or external provider fetch. Allow at most one client retry for a transient failure; honor `Retry-After` for throttling.

Before exposing the endpoint publicly, enforce a deployed shared IP rate limit of 30 lookup requests/minute, including failures. Verify the platform rule against the route and trusted client-IP behavior. An in-process limiter is insufficient on serverless instances. One client lookup may be active at a time. Use POST and `Cache-Control: private, no-store`; retain only the current review in browser memory. The immutable index is the bounded source cache; misses are not written as permanent negative records. No additional API key or FDC API fallback is proposed.

No frames, raw codes, private custom names, owner IDs or per-user scan history enter analytics, logs or shared caches. Operational metrics are aggregate outcome/timing counts with bounded retention. Platform request logs and throttling still need configuration verification; do not log request bodies. No new private metadata, schema migration, shared pantry ownership, or personal mapping-preference storage is proposed.

## BQ-03: reviewable suggestion coverage

The [45 source examples](../../catalog/proposals/2026-11-09-barcode-qualification/source-examples.json) preserve original USDA product fields, joined description/publication, source hashes, revision-group context and a per-record fingerprint. Sampling is purposive: all 32 previous staple discovery examples, the missing latest successor, and twelve additional food/form, mixed-product, spice, flour and dairy boundaries. It is not a random grocery-market sample.

[Mapping proposals](../../catalog/proposals/2026-11-09-barcode-qualification/mapping-proposals.json) recommend 16 exact current-in-snapshot source revisions for 11 identities: olive oil, avocado oil, apple-cider vinegar, coconut aminos, ordinary Worcestershire sauce, chicken broth, beef broth, ground cumin, garlic powder, all-purpose wheat flour and plain nonfat Greek yogurt. Each rule binds the original barcode/comparison key, US market, exact FDC ID, publication, snapshot fingerprints and source-row fingerprint. On any revision or evidence change, no suggestion survives without review. Only active, accepted catalog IDs may be offered. No generic catalog identity or compatibility edge is added.

The 29 holds include older superseded records, oil spray, lite coconut milk, frozen juice concentrate, marinades, soup, salad bowls, guacamole, prepared rice blends, smoked cumin, inadequately qualified chicken, and uncertain canned/whole-fruit forms. Bean categories and ingredient lists do not alone prove the exact canned form. A broth identity suggestion does not authorize fluid-volume pricing; an ordinary sauce match does not certify gluten-free status. A user may correct a held or unmapped product to a catalog entry, but that choice creates no shared rule and no component ownership.

Lookup coverage is **416,687 single snapshot product records** under this proposal; automatic suggestion coverage is **16 reviewed revision candidates**, not 416,687 ingredient mappings. A found but unmapped product still reaches manual catalog selection/custom entry and explicit confirmation. Real target-household barcode samples remain a launch verification need; the count is not a universal coverage claim.

## BQ-04: confirmation, decoding and rollout

Typed lookup precedes camera integration. Reuse the existing pantry identity/duplicate lookup and owner-bound queue. A separate review must show product details, proposed generic identity, editable catalog/custom selection and the user's current Yes/No status. Existing Yes is reused with optional details intact. Existing No changes only on explicit “Confirm addition.” Use the revision seen during review; a concurrent change must enter the existing conflict flow rather than silently saving a fresh revision. Double-click/retry uses the same pending operation. Cancelling, lookup refresh or source revision discovery never writes inventory. Package size is context, never a stock increment.

Increment a review generation and abort pending lookup on code change, close, owner change or navigation. Late responses and late camera permission results must be discarded; any late-acquired stream is stopped. A previously confirmed owner-bound mutation retains its existing retry semantics. Guest import stays explicit; product lookup never transfers inventory between owners. Custom entries retain existing no-recipe-match semantics. No product metadata needs to be added to exports/deletion because none is saved to personal records.

Recommend `@zxing/browser` **0.2.1** with `@zxing/library` **0.23.0**, restricting the reader to UPC-A/EAN-13. The isolated prospective entry is 485,193 minified bytes / 125,387 gzip bytes with esbuild 0.28.2; it is not the measured Next.js chunk. Package metadata gives MIT / Apache-2.0 licenses; include required license notices on installation and run the normal dependency audit. Import only after deliberate scan entry. Keep a native `BarcodeDetector` optimization optional and capability-tested; do not depend on it for Safari. [ZXing browser API](https://github.com/zxing-js/browser), [package manifest](https://github.com/zxing-js/browser/blob/master/package.json), [browser API availability](https://developer.mozilla.org/en-US/docs/Web/API/Barcode_Detection_API)

Request rear-camera preference only after a user action over HTTPS. Use inline/muted video playback appropriate to mobile browsers. Decode locally, pause after the first valid result, stop every media track and decoder control on close/unmount/page hidden/owner change, and require deliberate resumption. No frame upload or remote image URL decoding. Check the decoder's returned symbology as well as the string. Permission denial, missing camera, insecure context, unsupported format and decoder failure leave typed/search/custom entry available.

Separate lookup and camera environment controls default off; the existing pantry control and observed-pricing disable behavior remain independent. Ship typed lookup/confirmation first, then camera behind its own control. Disabling either preserves confirmed inventory, manual entry, pending owner-bound mutations and static/unpriced recipe behavior. No real iPhone Safari or Android Chrome camera verification was possible in this audit; permission, focus, narrow-screen layout, capture/close/resume, hidden-page cleanup and typed fallback must pass on both launch targets before camera activation.

## Reproduction and acceptance

Run `python3 scripts/audit-fdc-barcodes.py --input /path/to/retained/csv --output /new/operator/review --snapshot 2026-10-29 --expected-manifest docs/research/v1.6.2-staple-coverage-audit.json --samples catalog/proposals/2026-11-09-barcode-qualification/sample-ids.json`. Outputs include two local SQLite experiments, report and sample evidence; no runtime import is performed. Existing output directories and nested input/output paths are rejected. Failures leave an incomplete review directory to discard, never an active index. Keep the source and complete history in operator-controlled storage.

For decoder measurement, copy `decoder-probe-package.json` and `decoder-probe-package-lock.json` from the packet into a new isolated directory as `package.json` and `package-lock.json`. Run `npm ci --prefix /that/prefix --ignore-scripts --no-audit --no-fund`, then `node scripts/measure-barcode-decoder.mjs /that/prefix`. The probe resolves its pinned esbuild 0.28.2 from that directory, alongside the two decoder packages; it does not depend on repository-hoisted transitive packages. The application dependency/lock files are unchanged.

The 69-vector [expected fixture matrix](../../catalog/proposals/2026-11-09-barcode-qualification/fixtures.json) separates barcode/revision/mapping vectors from future flow and device checks. The executable audit tests cover equivalence and invalid inputs, revision ties, newest-discontinued handling, market separation, unknown dates, source integrity, malformed input, overwrite protection and reproducibility. They do not demonstrate a working runtime lookup, confirmation UI or camera. Required local repository checks and latest-head Copilot/CI/Preview remain documentation PR gates. Public lookup, camera and the full v1.6.2 release remain disabled/pending.

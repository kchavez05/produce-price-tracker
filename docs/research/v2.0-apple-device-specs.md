# v2.0 Apple Device Specs and Layout Breakpoints

Status: Research, checked 2026-11-12. Input to the [v2.0 specification](../specs/v2.0-ui-redesign.md) section 3a.

## 1. Sources and confidence

- **Stated by Apple:** diagonal sizes, pixel resolutions and pixel density from the [iPhone Duo tech specs](https://www.apple.com/iphone-duo/specs/), the [iPhone comparison page](https://www.apple.com/iphone/compare/) and the [iPad comparison page](https://www.apple.com/ipad/compare/). The iPhone page lists pixel counts landscape-first (for example 2868 x 1320); the table above swaps them to portrait. It does not label any model "current" and no base iPhone 18 appears, so the base model shown is the iPhone 17 (with the 17e and 16 still listed). The 17 Pro and 18 Pro rows share one size, as do the Max models.
- **Derived:** point sizes are pixels divided by the display scale. Apple's Human Interface Guidelines device table could not be retrieved (the page did not load its content), so scale is assumed: 2x for iPad, 3x for iPhone Duo. The outer Duo size (466 x 678) and the inner Duo size (626 x 890) match a third-party developer article, [iPhone Duo Apps: what changes in your code](https://pasqualepillitteri.it/en/news/15360/iphone-duo-prepare-apps-developers); Apple's own developer landing page ([Get ready for iPhone Duo](https://developer.apple.com/iphone-duo)) lists no numbers and links to the HIG pages for them. Verify the derived values against Apple's HIG device table before the layout lock.
- **Not available:** numeric safe-area inset values for any device. Do not hardcode them; read them from `env(safe-area-inset-*)` at runtime.

## 3. What this means for layout

- **Use size classes and width breakpoints, not device or orientation checks.** Apple's guidance for the Duo says orientation-based conditions give wrong answers on the inner screen.
- **iPhone range:** portrait widths run 390 (17e) through 393, 402, 420 and 440 (Pro Max), then 466 for the Duo outer screen, all compact. Design at 390 as the minimum and check 402, 440 and 466. The 390 x 844 wireframe size is exactly the iPhone 17e.
- **Proposed breakpoints (CSS width):**
  - Compact, below 600: iPhone, Duo outer. Bottom tab bar, single column, detail pushed full screen.
  - Medium, 600 to 1023: Duo inner (626 portrait, 890 landscape), iPad mini and iPad portrait. Icon rail, wider single column or two-column grid, detail as a sheet.
  - Wide, 1024 and up: iPad landscape. Full sidebar with list and detail panes. iPad mini landscape (1158) falls here.
- **iPhone Duo inner screen** lands in the medium layout (the same rail layout drawn for iPad portrait), so Duo support is mostly free if the breakpoints are width-based. The earlier plan to defer iPhone Duo is still reasonable for fold-specific behavior (partly open pose, hinge region).
- **Safe areas can be asymmetric on the Duo** (the camera sits on one side), so never assume equal left and right insets. Standard containers (scroll views, lists, navigation) handle reserved regions in native code; the web and PWA layer only sees the CSS `env(safe-area-inset-*)` values.
- **Fold and hinge:** Apple's native APIs expose reserved regions and a hinge angle. Whether and how Safari or the PWA exposes the fold to web content was not found; treat web fold awareness as unknown and out of scope for v2.0.
- **Touch and density:** all current iPads are 264 ppi except the mini (326); no change to the 44px minimum target.

## 4. Open items

0. **iPhone is portrait-only for v2.0 (decided 2026-11-12, owner).** Landscape iPhone widths (844 to 956) fall in the medium band (600 to 1023) but heights are only 390 to 440, so no landscape layout is designed or tested. A web app cannot truly lock orientation in Safari, so the rule is a fallback, not enforcement: keep the compact layout (tab bar, single column) whenever the viewport height is about 500 or less, regardless of width. That keeps landscape iPhone from switching to the rail layout; iPad (heights 744 and up) and the Duo inner screen (portrait height 890, landscape 626) are unaffected. A real lock arrives with the native apps (v2.x).
0b. **Manifest orientation check.** `src/app/manifest.ts` declares `orientation: 'portrait-primary'` for all devices. Verify whether iOS or iPadOS honors that for home-screen web apps; if it does, iPad would be locked to portrait too, which contradicts the landscape iPad layouts. Likely change: remove or relax it (to `any`) when the redesign ships.

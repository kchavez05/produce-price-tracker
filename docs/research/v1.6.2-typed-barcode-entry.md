# v1.6.2 typed barcode entry integration

The maintainer approved BQ-01–04 on November 10, 2026, against packet digest `f4888a5802f555b2919ed6b2ea6b5b9041876aa918153520c1d0a95299decb00`. The [decision record](../../catalog/proposals/2026-11-09-barcode-qualification/decision-record.json) preserves that approval separately from the immutable proposal. This integration implements typed lookup, correction and confirmation first. Camera support and public activation remain subsequent gates; independent observed-price permissions remain unresolved.

## Implemented flow

With the existing pantry and new lookup controls enabled, Virtual Pantry offers **Enter barcode**. Validated UPC-A/EAN-13 or typed consumer zero-filled GTIN-14 reaches the same bounded POST endpoint. Invalid/unsupported input retains manual search/custom entry. A found product shows its brand, raw package label, US market, USDA snapshot/publication/modified dates and source link separately from the proposed cooking identity. No package size becomes an inventory quantity or a recipe price.

Only the 16 exact approved revisions can suggest one of the 11 existing identities. An unaccepted or inactive identity cannot be preselected. Unmapped/missing/discontinued/date-held products retain manual catalog/custom correction. Ties require a product choice or manual correction; more than five tied records never produces an arbitrary truncated winner. The user must choose a cooking identity or private custom name and explicitly **Confirm addition**. Custom entries establish no recipe match.

The review captures the existing exact entry's revision and optional details, including quantity zero and old dates. Existing No is visible; confirmation alone changes it to Yes. Existing Yes and tombstones reuse the identity and preserve details. Changed remote revisions enter the existing conflict path. A fixed entry/mutation ID survives confirmation retry; duplicate clicks do not create another operation. Lookup, code changes, cancellation and source changes never mutate inventory. Changing owner unmounts the review and aborts pending lookup; late responses cannot populate the next owner's review. Confirmed queued writes remain bound to their original owner.

The hook's existing session, guest lock, account queue, authentication, RPC, retry and export/deletion paths remain in place. No Supabase schema/RLS/auth change or new private product metadata is introduced. Public lookup receives no owner ID. Responses are private/no-store; the browser retains only the current review. No camera frames, lookup histories or raw-code diagnostics are added.

## Build and configure the artifact

The original build procedure and receipts below retain their historical format. Current deployment uses the [lossless compaction procedure](v1.6.2-barcode-compaction.md) and its independently pinned pair; it preserves the full source/mapping coverage and the unchanged runtime query contract.

Requires the repository dependencies and Python 3.10+. Use the already retained CSVs; no FDC or Kroger API key is needed.

```bash
python3 -B scripts/build-fdc-barcode-index.py \
  --input /path/to/FoodData_Central_csv_2026-10-29 \
  --output /new/operator/barcode-build
```

The builder verifies the decision/envelope, both CSV hashes and all exact mapping fields, runs the reproducible audit, and produces `index.sqlite` plus `manifest.json`. It refuses existing output or nested source/output directories. Errors leave an incomplete operator directory to discard. Full source/history/audit files stay in that operator directory. **Copy only the two finalized files** into Git-ignored `data/fdc-barcode-index/` before a local or deployment build. Do not copy the audit subdirectory into the project. Retain complete source/history externally as specified in the packet.

The server checks the protocol, approved packet/mapping/source metadata, exact 16 mappings, artifact byte size and SHA-256, then opens SQLite read-only with query-only mode and extensions disabled. There are no runtime source downloads, writes, schema creation or fallback network searches. A missing, changed, corrupt or incompatible artifact returns a recoverable service result. The process retains one immutable read-only index; failures are not permanent negative cache entries.

Controls default off:

- `PANTRYBOT_PANTRY_ENABLED=true` is the existing pantry prerequisite.
- `PANTRYBOT_BARCODE_LOOKUP_ENABLED=true` exposes typed lookup.
- `PANTRYBOT_BARCODE_INDEX_DIR` optionally selects an operator-controlled local directory; the traced deployment default is `data/fdc-barcode-index`.
- Production also requires `PANTRYBOT_BARCODE_SHARED_LIMIT_VERIFIED=true` **after** verifying the deployed shared IP rule and trusted ingress behavior. The supplementary in-process limit is not a distributed limiter. It caps storage at 5,000 buckets, evicts expired buckets, and rejects new identities at capacity without resetting active counters. The ingress must overwrite caller-supplied IP headers before public activation.

`POST /api/pantry/barcode-lookup` accepts only barcode text and the declared supported format, capped at 256 bytes. The request stream and browser lookup each have a two-second deadline; the function ceiling is five seconds. HTTP results distinguish invalid/unsupported input, not found, ties, discontinued/date holds, disabled/configuration problems, throttling and service failure. Responses cap at 16 KiB. The UI honors `Retry-After`, aborts changed/closed requests, and never caches a failure as a confirmed miss. Current OpenAPI source and both exports describe the endpoint.

The feature remains disabled in committed configuration. Enabling a local development process does not authorize public activation. Before public enablement, deliver the pinned artifact through the deployment build, inspect the complete traced function size, verify read-only Node SQLite behavior and cold/warm deadlines in Preview, test the shared 30/IP/minute rule, verify authenticated fresh-session/two-client flows, and retain source-age/attribution disclosure. The local Next.js trace with the artifact contains 74 files totaling 116,821,316 bytes (about 111.4 MiB), including exactly the two artifact files. The approved packet and product data are absent from static browser chunks. This local trace is preliminary; the deployed function size and Preview behavior still need verification. No new paid provider or storage service is provisioned.
